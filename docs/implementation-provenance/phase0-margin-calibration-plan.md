# Phase 0 baseline variance and operational-margin plan

## Planner pass

### Objective

Close the Phase 0 evidence gate for the primary `full_match_offense` promotion target without changing the live r4 campaign. Produce a target-scoped v4 protocol only after (1) a complete D0 calibration bundle, (2) repeated matched-reference variance evidence on identical calibration seeds, and (3) an explicit, reviewed operational-margin decision. This work establishes calibration inputs; it does not qualify any A1/A2/A3/C1/C2 policy.

### Current evidence and gap

- The source plan requires measuring baseline variance before setting the minimum operationally useful improvement; it explicitly rejects inventing a universal percentage (`docs/MECO_AutoDrive_Learning_Tracks_Evaluation_Plan.md`, §§5–6).
- The checked-in protocol is provisional v1 with `gate_calibration_status=provisional_pending_baseline_variance_review`. The current qualification instructions require a complete prerequisite closure, immutable D0 bundle, repeated matched-reference bundle, explicit margin review, and v4 before promotion validation (`docs/MECO_QUALIFICATION.md`).
- The only checked-in D0 calibration report is `pickup_simple`: 1,200 rows, four strata, 100 seeds × 3 repeats. It does not cover the other 11 scenarios in the `full_match_offense` closure and its standard errors do not select margins (`docs/implementation-provenance/d0-pickup-simple-calibration-audit.md`).
- D0 calibration has resumable deterministic shards and full-campaign merge support. The default complete D0 schedule is 12 scenarios, 466 cases, 139,800 records (`docs/implementation-provenance/d0-campaign-orchestration.md`).
- Matched-reference calibration is implemented for exactly one preselected `D1/current`, `D2/cv`, or `D2/multi_model_v1` alongside D0, over the same repeated seed tables. Its current runner executes the whole scenario calibration in one process and has no shard/resume workflow (`docs/implementation-provenance/matched-reference-variance-calibration.md`). It binds K=16, the default route-cost weight, 12 action ticks, source and runtime identities, and all required safety metrics.
- The live r4 run is diagnostic and owns the two WX9100 device leases. Its exposure is not a calibration split and cannot be reused as calibration evidence. The run must remain untouched. The active source does not have a qualification binding or warm starts; no readiness or qualification claim follows from its progress.
- A hard prerequisite is currently unmet: `docs/MECO_QUALIFICATION.md` explicitly says host-side decision and analysis work remains, while the user requires algorithmic training, candidate generation/scoring, route/risk calculation, and statistical evaluation to stay on GPU. Device selection alone does not prove this. The existing matched-reference implementation only moved scorer arithmetic to the episode device; the D0 and matched-reference hot paths have not been audited or shown to satisfy the requested residency contract.

### Selected bounded tranche

The immediate prerequisite tranche is **GPU residency audit and closure for the D0 plus matched-reference calibration hot path**. The current repository evidence explicitly contradicts the requested GPU-only algorithmic contract, so neither calibration nor margin selection may begin after sharding support alone.

The implementer must trace and document the complete runtime call graph for D0 `calibrate-d0` and matched-reference calibration through `evaluate_meco`, including physics/state transitions, candidate enumeration, candidate scoring, route planning, opponent-risk calculation, safety metrics, and statistical aggregation. For every algorithmic operation, bind inputs, intermediates, and outputs to the selected indexed device, detect and reject implicit host copies, Python/CPU fallbacks, and CPU-only branches, and emit auditable per-stage device evidence in calibration records. Make unsupported operations fail closed instead of silently computing on CPU. The residency contract applies to both supported WX9100s and to D0 as well as D1/D2; proving only scorer placement is insufficient. Host activity that only schedules work or serializes already-computed results must be identified separately and must not perform algorithmic decisions or analysis.

The independent reviewer must verify the call-graph inventory and exact-device evidence contract against source and artifacts. Any implementation validation that requires a simulator/GPU workload waits until the live r4 run releases both WX9100s; then a bounded seeded residency acceptance run must demonstrate every required stage on the selected GPU with no CPU algorithmic fallback. If this residency tranche cannot close the path, explicitly defer all new empirical D0/matched-reference calibration, operational-margin selection, and v4 creation until a separate reviewed GPU-residency tranche closes it. Calibration readiness remains false meanwhile.

After that hard gate, implement and independently review **restart-safe, deterministic matched-reference calibration shards and merge** before launching the full calibration. Reuse the existing D0 calibration case/seed construction and immutable shard pattern, while preserving the matched-reference contract: each accepted row must bind the selected reference and D0 to the exact same `(scenario, case, repetition, seed)`, source, protocol, predictor mode, K, route-cost weight, cadence, normalized runtime, device attestation, and safety-metric schema. The merge must reject omitted/duplicate/unexpected assignments, mixed reference modes, source/runtime/config drift, missing safety rows, and any overlap with train/validation/test. Publication must be immutable/atomic and no-clobber. Keep D0 and selected-reference reports distinct in the final bundle.

This two-stage implementation sequence is bounded: GPU-residency closure first because the present documentation says the user requirement is unmet; matched-reference resumability second because that runner otherwise executes the complete scenario calibration in one process and can lose long-running work on interruption. The shard tranche does not unblock empirical calibration by itself. Neither tranche changes variance formulas, operational thresholds, qualification gates, D0 campaign semantics, policy behavior, Phase 4 work, or the approved legal-start profile plan. The existing `matched-reference-variance-calibration.md` remains the report/protocol contract; preserve legacy readers and exact validation.

### Run plan after the code tranche is reviewed

1. **GPU-residency gate.** Complete and independently review the D0 plus matched-reference algorithmic residency audit and implementation described above. Then, only after r4 is terminal and both exclusive WX9100 leases are demonstrably released, run the bounded seeded GPU acceptance scenario and inspect per-stage device evidence. Do not stop, pause, reconfigure, or compete with r4. If any required operation uses CPU or residency cannot be proven, stop: defer all empirical calibration, margin selection, and v4 creation until a separate reviewed tranche closes the gap.
2. **Lease and source gate.** After residency passes, reconfirm a clean, pinned checkout and HIP runtime on both physical WX9100s; bind each calibration manifest and worker to the exact indexed device, loaded native-extension identity, source hash, and normalized runtime.
3. **Freeze the statistical target.** Use `full_match_offense`, whose transitive closure is all 12 registered scenarios. Keep the existing calibration seed partition and master seed `20261024`, `episodes=100`, `repetitions=3`, with the protocol-declared case table (466 cases total). Do not regenerate or hand-edit seed tables. Confirm disjointness from all train, validation, and final-test assignments before scheduling. Use new immutable output roots namespaced to the exact reviewed source/runtime; never overwrite the existing `pickup_simple` report or its shards.
4. **Complete D0 first.** Resume/execute the existing 8-shard-per-scenario D0 campaign, merge each scenario report, then validate the immutable 12-scenario bundle. Preserve raw record coverage and provenance. Any rejected shard or changed source/runtime requires a new namespaced campaign rather than mixing outputs.
5. **Preselect one matched reference.** After D0 may be completed, but before starting any matched-reference variance collection or inspecting its variance outputs, record a short decision for exactly one supported variant (`D1/current`, `D2/cv`, or `D2/multi_model_v1`) based on the already-defined deterministic-control contract and intended primary comparison. Do not choose the reference by whichever has a favorable result on these calibration seeds. Bind it in every matched-reference shard; variant mixing is a hard stop.
6. **Collect repeated matched-reference evidence.** Run the new reviewed sharded runner for the same 466 calibration cases, exact seeds, 100 episodes per stratum and three repeats. Each assignment must evaluate the selected reference and D0 on the same case/seed and record useful throughput plus every declared safety metric. Balance shards across both pinned WX9100s only where normalized runtime equivalence is validated; keep shard-to-device provenance. Resume only digest-matching partial shards.
7. **Bundle and review margins explicitly.** Validate all 12 reference reports and the immutable bundle against the D0 bundle, seed-table hashes, source/runtime and reference identity. A named reviewer reviews per-case means, between-seed and within-seed repeat variance, uncertainty, tails, and every safety metric. The reviewer records the minimum useful-gain margins and safety non-inferiority margins in a separate immutable review artifact, with rationale, identity, timestamp, and exact report IDs/hashes. Do not calculate or auto-fill thresholds from a variance formula, and do not substitute statistical detectability for operational usefulness.
8. **Create and freeze v4.** Only after the explicit margin review is accepted, create and validate a `full_match_offense`-scoped v4 protocol binding the D0 and matched-reference bundle digests, source/runtime, reference variant, seed assignments, and reviewed margins. Keep the train/validation/final-test partitions unchanged and disjoint. The protocol's validation is a calibration-readiness gate, not evidence that a learned track passes the primary outcome gate.

### Device-dependent steps and hard stops

The following must wait until r4 releases both WX9100 leases: the seeded residency acceptance workload; native HIP preparation and attestation for calibration; all D0 shards not already backed by valid current-source/runtime artifacts; every D1/D2 matched-reference episode; any empirical variance calculation dependent on new rows; and any simulator behavior/replay work. Moreover, all empirical calibration, operational-margin selection, and v4 creation must wait for independent approval of the GPU-residency tranche, even if sharding implementation is complete. No calibration evaluation may fall back to CPU, a P600, a single card, synthetic data, or stale r4 records. Offline planning, implementation, review, schema inspection, and artifact validation can proceed while r4 runs, but they are not empirical calibration.

Stop the tranche if either card identity differs, any required algorithmic stage is not proven resident on its selected GPU, any CPU algorithmic fallback/host copy is observed, the native extension is unprepared or changes mid-campaign, source or normalized runtime identities drift, calibration seeds overlap a held-out split, a required safety metric is missing, or D0/reference pair coverage differs. Keep protocol status provisional and all qualification/promotion gates false until corrected evidence is independently reviewed.
