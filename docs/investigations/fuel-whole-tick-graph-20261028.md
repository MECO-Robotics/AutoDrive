# Experimental whole-tick FUEL graph

Worktree `codex/fuel-whole-tick-graph-20261028` is based on `a407d672c`. The source change in `frc_defense/fuel_physics_runtime.py` only enables the experiment with `AUTODRIVE_EXPERIMENTAL_FUEL_WHOLE_TICK_GRAPH=1`. It retains the same device-side stability bound and all 64 robot and FUEL substeps at the same timestep, capturing them in a single HIP graph. It binds reuse to current config, simulation, buffers and swerve settings; unexpected experimental capture or replay failure latches the simulator against future advances until reconstruction. The standard path retains its existing capture/eager fallback.

The old adaptive-count tests expected the pre-device-resident implementation: commit 2d1bd76a7 replaced `.item()` loop control with a device assertion and fixed max capacity. The archived FUEL benchmark notes a dense-pile stress scenario requiring up to 32 adaptive steps, so lowering the fixed capacity to the nominal 10 would not preserve the full stability envelope or identical trajectories. The relevant plan explicitly prohibits surfacing a device-derived count to Python.

A paired WX 9100 cuda:0 instrumented diagnostic on pickup_simple/cluster, seed 61720261028, teacher actions and a synthetic penalty, ran eight macros (78 ticks; four penalty-bearing decisions). Baseline `gpu0-baseline-r4-instrumented-goal-penalty.json` took 21.27538 s; candidate `gpu0-candidate-r2-instrumented-goal-penalty.json` took 17.86056 s, a 19.12% increase in throughput in this one instrumented pair. Candidate reused the same graph in all eight macro calls. Host spans overlap, instrumentation adds overhead, and this does not include A-track policy inference or represent a qualified training run.

The separate `trajectory.py` check then completed 24 seeded one-tick macros: 408 byte-exact comparisons across 17 robot, FUEL, owner, contact and simulator-clock tensors, identical CPU/GPU RNG states and done flags, and a single reused graph throughout. PyTorch reported peak reserved memory 83,886,080 bytes; this does not account for memory allocated outside the PyTorch allocator. See the candidate log and guard JSON. The fresh baseline replay `scenario-gpu-macro-goal-penalty-a455e432a68b2a024e2e` succeeded at 99 ticks with six acquisitions and is marked current on the isolated dashboard at port 18775; its index and six frontend assets matched the checkout.

The initial candidate replay was stopped by the guard at the configured edge temperature limit after the timing and trajectory checks passed. A subsequent guarded run completed a fail-closed capture-failure check and a fresh candidate replay. The forced error propagated without an eager fallback, restored the outer timestep, and preserved nine checked robot/FUEL state tensors. The final candidate replay `scenario-gpu-macro-goal-penalty-93b279bef78374ae0c89`, generation `5837cc67d95546e0ac7fc54e3d15ccf8`, succeeded at 99 ticks with six acquisitions. Its frames, decisions, outcomes, ticks and penalty hash exactly matched the final-source baseline replay. The isolated dashboard reported both records current and served its index and six frontend assets from the checkout. These replays used the final runtime code before the review commit; a fresh post-commit replay is required for commit-level dashboard provenance.

Independent review identified that callers could retry after a capture error. A persistent latch now blocks subsequent advances after a failed experimental capture or replay; focused CPU tests inject state mutation, catch each failure, and verify a second call is rejected before further stepping. The timings and replay above predate this latch and require final-source revalidation.
