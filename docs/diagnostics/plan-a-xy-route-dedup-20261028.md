# Plan A XY route deduplication diagnostic

The Plan A pose graph contains eight heading rows for each planner grid cell. The shared XY route evaluator uses the robot's current pose and heading and does not consume the destination heading. The candidate evaluates each planner cell once, then expands all route tensors to the original pose-node order with original query IDs and indices. A device-side check rejects same-capacity graphs whose coordinates are not exactly eight copies of the planner grid; graphs with other capacities use the original path.

On cuda:0 with an exclusive device lease and post-lease device attestation, the diagnostic compared the candidate against f87acd21c using a real `pickup_simple` / `single` scenario (seed 71) and its 12,096-node pose graph, using a synthetic mixed support mask. For both unweighted and learned P costs, route tensor fields, query identities, mask, fallback, order digest and route evidence digest were exactly equal. Route statuses included at-goal, invalid and no-path rows. The altered-grid check rejected all routes and selected fallback -1.

Unweighted baseline calls took 39.18 and 20.83 seconds; candidate calls took 2.73 and 2.72 seconds. The first baseline included native startup. Learned-cost baseline calls took 10.52 and 10.36 seconds; candidate calls took 1.49 and 1.41 seconds. These are route-stage timings for one scenario and should not be interpreted as end-to-end training throughput. Raw output is at `/mnt/zfs-storage/All Drives/Brian Data/Projects/AutoDriveDiagnostics/ppo-capture-20261028-seed42-attempt5/xy-dedup-full.txt`.

The diagnostic source preprocessor reformatted `frc_defense/csrc/tensor_collision_multi_hip_kernel.hip` during native initialization; the incidental change was restored after the run, so the run did not use a byte-identical final working tree. The diagnostic uses a lease and attestation but does not check global device overlap or thermal limits. It did not produce a simulator replay or validate current dashboard services. End-to-end A rollout validation, a fresh replay and dashboard verification, wider scenarios, and integration with other route changes remain necessary before production use. The production A route gate was not changed.
