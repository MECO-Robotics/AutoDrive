## Required implementation handoff after coordinator integration

Do not reimplement or modify the in-flight multi-case coordinator's shard, combine, receipt, or test-fix logic. First audit the integrated coordinator's exact accepted target schemas and output paths. Then implement only any demonstrated missing glue from this list, in separate scoped implementation/reviewer passes:

1. **One production bundle validator/consumer boundary.** Provide a command or narrow adapter that takes the integrated multi-case descriptor and complete-set manifest, recomputes the combined C and A dataset/sidecar hashes, reruns the actual C1/C2 and A1/A2/A3 artifact validators, and checks every artifact against the same exact case-set digest, frozen protocol bytes/partition, source identity/tree, prediction contract, runtime/native identity, device identity, split and attempt. Reject any target-family/case omitted from a declared complete case set, mixed attempts, missing P for a declared U+B+P bundle, stale artifact bytes, or a readiness/qualification claim. Emit one machine-readable receipt with per-case/per-track counts, coverage denominators, artifact hashes, and explicit `training_readiness_proven=false`, `phase2_complete=false`, `qualification_eligible=false` until the corresponding evidence gate is met. Reuse existing validators; do not create parallel permissive schemas.
2. **No hidden target conversion.** Bind C's repeated matched rollouts, gross-return and tie/variance evidence through the combined input and C warm-start; bind A's U target to the legal-node replay evidence and feasible B preferences to the supported pair records; bind P to the separate executed-route/oracle dataset. Keep human-authored annotation inputs explicitly declared and authority-hash-bound if the selected A path needs them. Never convert teacher actions, aggregate match score, or an unavailable/censored target into an optimality label or zero.
3. **Fresh manifest handoff.** Use the five-track complete-set warm-start map and bundle receipt to generate a new isolated campaign config/manifest from the latest reviewed settings. Validate the result through `meco_training_manifest` and `meco_supervisor` before launch. Assert exact A1/A2/A3/C1/C2 path/hash set and preserve each artifact's dataset and case-set bindings. Use new absent checkpoint, evaluation, replay and campaign roots; never mutate r4 config, outputs, worker state, or checkpoints.
4. **First-chunk initialization evidence.** Preserve the supervisor run record and each worker's initialization record showing `weights_only_supervised_warm_start`, exact per-track warm-start SHA, source/protocol/case-set binding, and first update/chunk. Reject resume mode or an initialization record missing any artifact binding. This demonstrates consumption; it does not establish learning benefit or qualification.
5. **Review surface.** Add concise artifact/run instructions to `docs/MECO_SUPERVISED_WARMSTART.md` and update `docs/MECO_FULL_PLAN_EXECUTION_STATUS.md` only with observed results. Do not claim data coverage, readiness, or GPU/simulator validation from offline tests.

These are conditional implementation items: if the integrated multi-case coordinator already provides an item and the independent reviewer verifies it end-to-end, record the API and evidence and do not duplicate it.

## Runtime data and warm-start execution (separate from implementation)

Runtime work is blocked until the live r4 supervisor ends naturally or the user explicitly stops it, all its workers exit, and both shared WX9100 leases are free. Do not signal r4, rewrite its STOP/status/checkpoints, or launch competing GPU/simulator work while it owns the cards. A code merge, elapsed time, or user request to keep r4 uninterrupted does not release this gate.

After that gate, use a clean isolated checkout at the independently reviewed source commit and a newly numbered output attempt outside the checkout. Follow this order:

1. Pin and validate the current qualification protocol bytes and the integrated coordinator descriptor for the explicitly declared full train-case closure. Keep validation/final-test cases and seeds disjoint. Do not call a selected subset full-protocol closure; record exact per-case coverage and identify partial coverage as such.
2. Acquire the shared indexed-device lease, then attest the actual physical WX9100 by PCI BDF, product, vendor/device and HIP UUID against the hash-pinned host inventory. Require the Phase 2 routing/physics GPU path to pass its exact-output parity and profile gates on that attested device. Fail closed on mismatch, missing property, CPU Dijkstra/fallback, or P600; do not start collection or fitting before these checks pass. Persist lease/device evidence with the attempt.
3. Execute the reviewed multi-case coordinator serially under the exclusive device lease, reusing only immutable validated shards for the same descriptor. Gather the matched-prefix v3 source once per declared case/seed; replay every source and target branch through the exact archived observation, support, candidate, descriptor and executed-action trace. Retain repeat-level outcomes, common-random-number pairing, tie/uncertainty/censoring status and source/sidecar hashes.
4. Produce the C1/C2 targets from the same declared candidate set and source corpus, with repeated matched gross-horizon returns and non-tied within-prefix pairwise preferences. Produce A1/A2/A3 U+B from strict replayed legal support with the declared coverage rule, and P from separate replayed P-shaped route traces with independent route-cost oracle labels. If the live, attested P route path is unavailable or fails replay/parity, stop the attempt and do not represent the A artifact as U+B+P or Phase 2 complete; the declared fallback is a separately named U+B `p0` diagnostic artifact and cannot satisfy the U+B+P acceptance gate.
5. Fit all five models only on the attested indexed WX9100 path. Validate each weights file using the existing track-specific loaders/validators and the production bundle validator; re-open the published bundle and recompute hashes and per-case coverage after publication. Preserve immutable attempt receipts and failure journals; retry into a fresh attempt or use coordinator-supported resume after exact byte revalidation.
6. Generate and validate a fresh five-track training manifest that consumes those five exact artifact paths. Launch only when both WX9100 identities are attested under the supervisor's two-device lease and the prior campaign is terminal. Observe each track's first initialization record and hash before treating warm-start consumption as established.

Collection and fitting are training-data production, not game-behavior validation. Their internal prefix replays support label integrity, but do not by themselves satisfy the project requirement for a representative end-to-end learned-policy simulator evaluation and inspected replay.

## End-to-end behavior verification after consumption

After the new five-track supervisor has consumed the five artifacts and produced comparable checkpoints, run a separate predeclared end-to-end simulator evaluation against D0, matched D1 and D2 using identical held-out cases/seeds and information. Preserve evaluation configuration, source/checkpoint hashes, environment/candidate/action contracts, all five scorecards and paired interval calculations. Use held-out opponent families rather than only random seeds from a seen policy. Do not derive model selection from training-case metrics.

For any run that checks simulated behavior, retain a reproducible scenario/case and seed and inspect its record/replay for actual selected actions, legal route, executed mechanism actions, scoring/collection outcome, safety and terminal metrics. Before making or reviewing the replay, restart the dashboard services from the exact current checkout; verify backend/API and frontend asset hashes/current source identity, then generate a fresh replay and mark earlier-source replay data outdated. Record replay ID, seed, dashboard process/source identity and inspection result. If any expected behavior record/replay or dashboard-currentness evidence is unavailable, state that the gate failed; do not substitute unit tests, a fit receipt, a synthetic replay, a dashboard projection, or optimizer-update counters.

Passing this Phase 2 verification does not close the source plan's Phase 0 calibration, Phase 3 RL, Phase 4 adversarial/generalization, Phase 5 deployment profiling, held-out statistical success threshold, or final qualification gates.

## Acceptance criteria

1. **Coordinator dependency:** the reviewed integrated multi-case API describes an exact train-only case set and supports immutable resumable shards/combination. The exact in-flight implementation head and reviewer decision are recorded before any downstream implementation or runtime data is produced.
2. **Five valid targets:** A1/A2/A3 each have replay-verified U+B and independently replay-verified P under one shared declaration (or an explicitly non-completing p0 artifact); C1/C2 each have matched pairwise gross-return supervision. Every track artifact binds the same full declared case-set, exact protocol bytes, source identity, train split, prediction semantics and attested device. Counts and coverage denominators are reported per case and target family.
3. **Full production validation:** the production consumer reruns dataset, sidecar, stage receipt, and artifact validators; recomputed bytes equal every receipt. Missing or duplicated cases, train seeds, decisions, candidate/node support, target family, or repeated branch evidence fail closed. No claimed readiness exceeds the underlying per-case target and replay evidence.
4. **Supervisor consumption:** one fresh manifest includes exactly the five validated warm-starts, and a fresh supervisor/worker record proves each track initialized from its exact artifact hash in weights-only warm-start mode. No r4 output or initialization is repurposed.
5. **Device proof:** before any collector/fitter/supervisor worker starts, leases bind to both physical WX9100 identities; collection, route construction and fitting pass the GPU-only/HIP parity profile gate with no CPU fallback. Identity and runtime evidence is retained.
6. **Behavior proof:** current-source matched held-out evaluation covers all five tracks and controls; the AGENTS-mandated fresh seeded end-to-end replay is inspected after a verified current-dashboard restart and current frontend/backend check. Report exact scenarios/seeds, replay IDs, metrics and paired intervals. No performance or qualification claim without these artifacts.
7. **Incremental scope:** code work is split into planner, implementation and independent exact-head review; this plan and implementation changes are committed/pushed in small increments. No simulator/GPU training/evaluation is launched by offline implementation tests. Root's unrelated modified HIP file remains untouched.

## Explicit non-claims until evidence exists

- A complete-set seal or supervisor manifest is not proof that simulator behavior works.
- Five optimizer chunks, one hundred updates, or any other update count is not a curriculum pass or held-out evaluation.
- A training split with every declared row is not held-out generalization; selected-case closure is not full protocol closure.
- Teacher agreement is not expert optimality. An oracle-cost preference is only as valid as its replayed route and independently specified cost contract.
- `phase2_ready` or campaign launch readiness is not `phase2_complete`, qualification eligibility, or successful model promotion.
