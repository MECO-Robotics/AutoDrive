# Whole-compute GPU residency for MECO qualification

**Status:** Pass 1 plan candidate only. This artifact authorizes planning only; it does not authorize code changes, tests, calibration, campaign edits, training/evaluation, device access, or service operations.

**Planning base:** `664092b93467fd926d8bb74e8e04f311489000c4`.

## Objective and contract

Close the gap between the user's explicit requirement, “offload everything to GPU: no CPU,” and the current MECO v4 qualification/training/evaluation implementation. All algorithmic and numerical work must execute on an explicitly assigned WX9100 GPU, including:

- policy training updates, including forward/backward passes, loss/advantage calculations, optimizer updates, replay/batch math, and reductions;
- environment-side candidate generation and candidate feature calculations;
- policy scoring and action selection;
- route generation/cost, path-risk, forecast-risk, and safety calculations;
- calibration, paired candidate/reference evaluation, and statistical summaries, including the category-level clustered bootstrap confidence intervals used by v4.

CPU may perform only non-compute orchestration and file/network I/O that is necessary to launch work, move serialized artifacts, and present completed results. CPU code must not calculate a candidate, score, route/risk value, gradient/update, calibration statistic, confidence interval, or policy/evaluation decision. Moving a result tensor to CPU is allowed only after its algorithmic result is final and solely to serialize or display it. No CPU fallback is permitted.

The later qualifying runtime must use exactly the two assigned WX9100 devices with exclusive per-device leases. Evaluation and training may run at the same time only on different GPUs. If an evaluation owns one GPU, training continues on the other; multiple training lanes are scheduled fairly on their leased device, not concurrently on the same device. All five lanes must receive non-starved progress. The live r4 diagnostic campaign remains unchanged and uninterrupted until the user manually stops it.

## Audit basis: existing gate and missing residency

The qualification rules already exist and should remain the source of truth. `frc_defense/training_curriculum.py` implements validation-only category gates, minimum episode counts, category-level success thresholds, unique evaluation IDs, same-protocol consecutive passes, and persistent promotion state. `frc_defense/meco_qualification.py` has a v4 validation path that binds source/protocol/checkpoint/reference identities, checks exact case rows and seed lists, computes category-level paired-throughput and safety CIs using complete layout/family clusters, and passes its failures into the promotion decision. Its CLI stores state for one candidate policy per state file. The exposure scheduler remains separate and reports promotion as not evaluated.

That gate does not establish GPU residency. `docs/MECO_QUALIFICATION.md` explicitly says the current user's requirement exceeds the legacy indexed-GPU contract: only selected scorer arithmetic has moved to device, while other host-side decision and analysis work remains. In the current source, `_cluster_bootstrap_ci` in `meco_qualification.py` performs resampling and means in Python loops; `_route_cost_tensor` in `meco_track_training.py` receives Python-built route records and creates a tensor only afterward; and candidate/route/risk paths contain CPU materialization and scalar/list conversion. Some conversions are report serialization, but each call site must be classified by whether it feeds a later decision or calculation. A `cuda:N` validation or “no fallback” flag alone is not evidence of whole-compute residency.

The current supervisor is a diagnostic training/evaluation orchestrator. It marks campaign qualification false and its integrated evaluation output is diagnostic-only. Do not repurpose that state or weaken the separate v4 admission and promotion gate.

## Bounded execution sequence after Pass 1 approval

Each numbered stage is a separate, reviewable tranche. Approval of this plan does not approve any later execution.

1. **Keep the live campaign isolated.** Continue r4 without editing its checkout, manifest, checkpoints, scheduler, leases, processes, or output tree. Do not access its devices. Develop changes only in an isolated HDD-backed worktree. Do not merge or copy changed source into r4's checkout. No test, profile, calibration, simulator, or qualification workload may compete with r4 while it is active.
2. **Inventory every compute boundary.** Map the full five-track training, candidate-generation/scoring, route/risk, simulator, calibration, paired-evaluation, bootstrap, and report paths. For each operation classify tensor device, producer, consumer, host transfer, whether that transfer is serialization-only, and fail-closed condition. The inventory must cover Python loops and scalar decisions as well as explicit NumPy/CPU kernels. Confirm intended ROCm/HIP runtime and actual WX9100 identities through an approved later device-readiness tranche, not in this planning pass.
3. **Move algorithmic calculations onto device.** Keep candidate batches, features, masks, legal-action decisions, route/path costs, forecast/risk features, advantages, returns, losses, optimizer math, and statistical samples as tensors on the assigned device. Port CPU-generated candidate and route/risk features to device kernels/tensor operations. Keep Python only for orchestration and serialization; a host loop that calculates or branches on an algorithmic value is compute and must be removed. Retain conversion to host only after a result is finalized and solely for immutable report/replay serialization.
4. **Port qualification statistics without changing their estimand.** Implement deterministic device-resident sampling for v4's paired category-level bootstrap. Preserve the frozen resampling semantics: sample complete `(layout_id, defender_family)` clusters, then episodes within each selected cluster, and calculate candidate-reference useful-throughput and candidate-reference / candidate-D0 safety intervals on GPU. Keep complete frozen-stratum and exact-seed coverage checks. Bind any changed bootstrap implementation and semantics into the source/protocol identity; do not silently reuse old calibration margins or old v4 reports.
5. **Add fail-closed GPU and lease admission.** Before work starts, require an explicit indexed HIP device, expected WX9100 identity/backend, and an exclusive lease. Reject CPU device aliases, CPU tensors at compute boundaries, accidental `.cpu()`/`.numpy()`/host scalar paths that affect a decision, mixed-device tensors, unavailable devices, wrong device identity, lease conflict, and failed GPU residency assertions. Add boundary checks for model parameters, environment state, candidates, scoring, routes/risks, training updates, calibration, and bootstrap output. Any failed check aborts the current job and publishes a bounded failure report; it must never silently switch device or mode.
6. **Schedule the two GPUs without contention.** Use one exclusive lease per WX9100. While v4 evaluation occupies one device, schedule training work on the other and advance A1/A2/A3/C1/C2 with a fair, non-starving queue. Defer lanes when their device is leased, then resume from their latest compatible checkpoint after release. Never overlap training/evaluation compute on the same GPU, and never count queued or deferred work as progress. Record per-lane updates, job/device/lease IDs, checkpoints, evaluation report IDs, and failure/retry state. A lost device or lease is a fail-closed stop, not a CPU fallback.
7. **Prove the implementation before source freeze.** In a separate implementation branch, complete static call-site review, device-boundary checks, performance profiling, and representative seeded end-to-end simulator evaluation with inspected record/replay after the campaign is stopped and the GPUs are released. Verify that every compute operation is GPU-resident and that host copies are serialization-only. When behavior tests run, follow repository `AGENTS.md`: inspect the changed behavior in a representative simulator record/replay; restart and verify dashboard backend and frontend currentness before replay generation. No such verification is part of this planning tranche.
8. **Freeze source/runtime only after all code is final.** Record the final source commit and `curriculum_training.source_identity()` digest, source-tree projection, all relevant environment values, compiled native HIP extension identity, Python/PyTorch/ROCm runtime, simulator identity, track configs, and two device identities. `source_identity()` hashes source/config files under `frc_defense` as well as runtime environment/native identity; adding or editing any included source after freeze changes the binding. Complete all GPU-residency, qualification, reporting, and dashboard code before this freeze. Then treat source/runtime as immutable for calibration and promotion.
9. **Calibrate and generate v4 against the frozen implementation.** Only after source freeze, produce source-bound D0 calibration, matched-reference repeated variance evidence, reviewed useful-throughput and safety margins, and a new immutable calibrated v4 protocol using the GPU-resident evaluator/statistics implementation. Bind protocol ID, calibration/source/runtime hashes, exact strata and seeds, margins, bootstrap implementation identity, reference checkpoint identity, and safety schema. Existing provisional v1, historical D0, previous-source v4 artifacts, and diagnostic r4 reports cannot be reused as current-source qualification evidence.
10. **Resolve checkpoint compatibility and launch only after readiness.** After the user manually stops r4 and its device leases/processes are confirmed released, snapshot each latest checkpoint and its exact training provenance. Current checkpoint loaders require payload `sources` to equal the current `source_identity()`; the v4 evaluator likewise rejects a checkpoint whose source map differs. Compare exact checkpoint, model, config, runtime, extension, and source identities before reuse. Do not bypass the loader or rewrite a checkpoint's source binding. If the GPU/source change makes a checkpoint incompatible, stop and report the exact mismatch for a separate decision; do not assume from-scratch training. A fresh qualifying campaign must be separately approved, bind the frozen source and v4 protocol, pass all training-manifest/readiness and GPU-only gates, and use fresh unique output paths. It must never modify or resume r4.

## Acceptance evidence for a later implementation

The GPU-residency gap is closed only when a separately reviewed implementation has all of the following evidence:

- A complete call-site inventory covering training, candidate generation/scoring, route/risk, simulator, calibration, paired evaluation, and statistical summaries. Every numerical/algorithmic path is GPU-resident; each host transfer is documented and only serializes a completed result.
- Runtime instrumentation and profiler evidence showing the expected indexed WX9100 owns model/environment/intermediate/statistical tensors and executes every compute kernel. No CPU arithmetic, tensor fallback, or CPU statistic is observed. Deliberate CPU-device, wrong-device, lost-device, missing-lease, and mixed-device conditions fail before silently producing a result.
- GPU bootstrap results match frozen deterministic protocol fixtures and preserve complete paired cluster resampling, margins, coverage, and CI semantics. Reports bind implementation/source/protocol identities.
- Supervisor evidence of exactly two exclusive WX9100 leases: validation uses one device while training progresses on the other; all five lanes receive non-starved progress; no GPU has overlapping jobs; no evaluation terminates training; and deferred lanes resume from identity-checked checkpoints.
- Source/runtime identity is frozen only after all source edits; v4 D0/matched-reference calibrations and reviewed margins are bound to that exact identity. No old-source or diagnostic result is represented as qualification evidence.
- Every subsequent formal promotion still satisfies the existing v4 gate: complete exact frozen case/seed coverage, at least 100 episodes per category per stratum, category-level success threshold, three consecutive passing rounds per policy under the same protocol, category-level useful-throughput and safety CIs from the frozen GPU cluster bootstrap, and exact policy/reference/D0/checkpoint/source binding.
- For behavior-changing verification, a reproducible seeded end-to-end simulator record/replay is inspected and dashboard backend/frontend currentness is verified before replay generation. The report records scenario, seed, replay ID, CI/evaluation report IDs, devices, and outcomes.

## Stop conditions

Do not start any implementation workload, GPU profile, calibration, simulator evaluation, or qualification run while r4 is using the devices. Stop a later run before compute if either WX9100 identity/lease is missing, any compute path is CPU-resident or unclassified, the GPU statistic implementation is not bound by source/protocol identity, source/runtime hashes drift after calibration, checkpoint compatibility is unknown, or v4 calibration/margins/readiness are incomplete. Never change r4, force a CPU fallback, or label diagnostic evidence as qualification. Any necessary source migration or retraining decision requires a separate review after exact checkpoint provenance is available.
