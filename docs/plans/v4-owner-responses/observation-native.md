## Source-resolved identity and lifecycle

The V4 owner matrix settles the identity category: a target handle identifies an anonymous observation track, not a physical gamepiece ID (matrix, lines 82–83). I adopt that meaning for this row. In particular, `observer_slot` is the observing robot, `buffer_slot` is that observer's track-array index, and `slot_generation` distinguishes successive anonymous track allocations in that buffer. The handle is not a localization claim that the same physical piece remains associated through every update.

The source supports these lifecycle facts:

- `frc_defense/tensor_3v3.py:368-379` allocates per-world, per-robot arrays for track position, velocity, mask, age, confidence, extents, and visibility; the track arrays have no piece-ID or generation column.
- In the HIP tracker, `frc_defense/csrc/tensor_perception_hip_kernel.cu:861-872` increments active-track age and clears `track_mask` after timeout. Lines 911–943 associate detections to nearby active slots or choose the next free slot; lines 959–975 write new measurement state and set that slot valid. Thus slot occupancy is observer-local and anonymous. A handle to a slot whose mask was cleared is no longer live; reusing an empty slot creates a new allocation even if the detection may represent the same real piece.
- The non-fused association path in `frc_defense/_tensor_3v3_observation.py:554-572` likewise associates detections to existing slots, updates the chosen target, resets its age, and sets its mask. It does not provide physical piece identity.
- `frc_defense/_tensor_3v3_gamepieces.py:83-94` initializes `_meco_world_reset_generation` and increments it for reset worlds on subsequent fuel initialization. Full reset and partial reset clear observation track masks in `frc_defense/tensor_3v3.py:571-576` and `:643-649`. Therefore an observation handle must include the current world reset generation; a reset invalidates every old handle for that world regardless of its buffer index.
- The V4 contract explicitly requires incrementing slot generation on allocation/reuse, including an expired-but-still-masked entry; incrementing reset generation on reset; no wrap; and fail-closed exhaustion (proposal, lines 274–280). Those rules are compatible with the observed tracker lifecycle. For a matched update to a currently valid track, retain slot generation. When a detection is assigned to a slot without a live track, advance that slot's generation before marking the new track valid. If a track has expired by age but its mask has not yet been cleared at the allocation boundary, treat it as expired, advance generation before reuse, and invalidate its old handle.

For the V4 interpretation, `slot_generation` is a nonnegative counter per `(environment instance, world, observer, buffer slot)`, starting at zero and incremented before each new anonymous-track allocation. It persists across episode resets for the lifetime of that environment instance; reset generation independently fences all handles from earlier resets. A matched detection update retains generation, including when the association changes the estimate's physical referent: the stable identity is the allocated observer-track slot lineage, not physical continuity. The maximum representable value is signed int64 max; if increment would exceed it, fail closed before publishing a new track/action and never wrap or reuse a generation. V4 assigns validation status 12 to overflow (proposal, lines 260–265). Apply this no-wrap rule to all V4 identity counters, including reset generation and observation sequence. This is an owner-level normative interpretation of V4's stated no-wrap/exhaustion rule, not a claim that the current source already implements a generation counter.

## Handle validation and physical score-event separation

V4's intended validation unit is the complete handle plus the observation snapshot that produced the action: `target_handle=(world_reset_generation, observer_slot, buffer_slot, slot_generation)` and `snapshot_token=(environment_instance_id:uint64[2], world_slot:int64, robot_slot:int64, world_reset_generation:int64, observation_sequence:uint64)` (proposal, lines 149–153 and 274–280). A consumer must reject a handle if its environment/world/observer/reset scope differs, the stored slot generation differs, the slot is masked invalid, or its age exceeds the configured track timeout. It must never reinterpret a stale handle by reading whatever new track currently occupies the same buffer slot. An observation snapshot token binds the originating policy decision; it is not a requirement that the track handle become invalid merely because later observations were produced during the same macro. Slot/reset generations and current validity determine whether that target track remains live.

The current planner consumer at `frc_defense/tensor_3v3.py:789-798` receives only an integer track index and checks mask, age, finiteness, source-position distance, and action match. `_run_macro_step` in `frc_defense/meco_track_training.py:1883-1909,1923-1932,1962-1969` keeps that index while it advances the macro and masks later execution after target loss or action mismatch. Neither path currently validates a generation-bearing handle. The distance check is a useful current guard but is not equivalent to handle validation: a newly allocated track could reuse that index and lie near the previous target. The V4 consumer must carry and validate the full handle across the action boundary.

Observation identity must remain disjoint from score-event identity. The V4 score-event row contains physical `piece_slot` and `piece_generation` (proposal, lines 199–212). `frc_defense/gamepiece_actions.py:22-24,43-69` captures the simulator's actual chosen piece mask and `_meco_piece_generation` when score awards are queued, and `:484-488` advances that physical-piece generation on scoring. `frc_defense/meco_simulated_score_ledger.py:315-337` validates the physical slot/generation incarnation. There is no source-supported conversion from an anonymous observer track handle to those fields. The score owner must continue to use simulator piece identity and must never copy `buffer_slot` or `slot_generation` into `piece_slot` or `piece_generation`; there is no join between these identity domains in V4.

## Snapshot and macro projection

The snapshot tuple is clear at the field/type level (V4 proposal, lines 274–280), but source coverage is partial. `frc_defense/learning_contract.py:24-49` defines `ObservationSnapshot.sequence` and `snapshot_id`; `frc_defense/meco_candidates.py:1272-1280` binds the candidate snapshot to the current simulator step, checks that sequence, and names it `episode_id:sequence`. Accordingly, the V4 `observation_sequence` is the current world's simulator step at the policy observation capture boundary after perception has been updated; the `world_reset_generation` separates step values reused by later episodes. The current source does not establish that this counter is monotonically increasing within an episode if the simulator step counter can wrap, so the implementation must reject exhaustion rather than wrap. It also has no `environment_instance_id:uint64[2]` producer. The uniqueness domain and issuer for that environment identity remain an open implementation-contract decision.

V4 defines a fixed `T=12` macro trace with `tick_valid`, `executed_action`, `remasked`, `target_lost`, `preempted`, `fallback`, `execution_valid`, reward, gamepiece outcome flags, and status (proposal, lines 160 and 265–270). `_run_macro_step` records a variable-length sequence up to `action_ticks`, stores per-iteration active flags and executed actions, can terminate early on done/truncated, and aggregates rewards (`frc_defense/meco_track_training.py:1903-1909,1915-1932,1961-1995,1997-2021`). Source supports `target_lost` and action-remasked signals, terminal/truncation, selected action, and score/pass events, but it does not currently define a canonical per-tick `fallback` or `execution_valid` producer or a complete fixed-width serializer. The 12-tick field bound is therefore a V4 profile contract and requires the environment/profile owner to bind `action_ticks <= 12`; the native macro call path alone accepts any positive `action_ticks` (`frc_defense/meco_candidates.py:1264-1269`).

## Remaining explicit gates

These gaps are not resolved by current producer/consumer contracts and remain PENDING rather than receiving inferred values:

1. **Environment identity:** choose and implement an issuer/uniqueness domain for `environment_instance_id` so it cannot alias another environment in the artifact's provenance domain. Existing episode IDs are not source-proven globally unique environment-instance identities. Counter exhaustion for the `observation_sequence` derived from simulator step must fail closed without wrap, as V4 requires.
2. **Macro trace producers:** define exact `fallback` and `execution_valid` predicates and fixed-tail values for ticks after early terminal/truncation or target/action remasking. Bind the selected `action_ticks` limit to `T=12`. Preserve V4's status precedence and check that per-tick outcomes and summed reward agree with the existing macro record.
These are limited to observation/native plus the stated profile and score-event dependencies. They do not justify changing the pinned V4 artifact. The observation/native disposition remains **PENDING** until the above decisions have a reviewed contract; this is not an unsubstantiated rejection and no replacement is proposed.
