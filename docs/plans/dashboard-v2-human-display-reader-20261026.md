# Pass 1 plan: non-gating dashboard reader for device-produced v2 records

**Status:** Proposed; Pass 2 requires independent Pass 1 approval and the upstream schema gates below. Pass 3 reviews the exact integrated head.
**Planning base:** `origin/main` / `main` `5afe639760a3e5ebef4ee392901dca55aa5e15c8`.
**Scope:** provide a usable human replay/record view for immutable device-produced v2 evidence while preserving the strict whole-compute boundary. This plan does not change record producers, training/evaluation, qualification, campaign readiness, or existing v1 dashboard behavior.
**No runtime action:** no services, tests, simulator/replay, campaign, checkpoint, GPU or device action is authorized by this plan.

## Versioned human-display-only exception

Define this exception as **`meco-dashboard-v2-human-display-reader-v1`**, consuming only the canonical device-produced v2 envelope defined jointly by the **accepted shared ABI** and the **exact accepted PPO owner plan**. V2 denotes the producer-owned record/envelope version; this dashboard plan does not define its serialization. Enable the reader only after the PPO plan pins the exact envelope, immutable artifact/pointer layout, and provenance registry, and compatible owner contracts are accepted. The reader decodes completed bytes solely to draw and label the replay for a human. It does not authorize new calculations from those values.

The reader may render per-record/per-tick values verbatim: scenario and seed, policy/track, action and selected-versus-executed identity, local/global row and descriptor, goal/route, per-tick remask/fallback/preemption/terminal events, observed gamepiece frames/events, and reward/score values already present in the device record. It may format those individual stored values for legibility, synchronize a human-selected timeline cursor to recorded frames, and display producer-supplied labels. It may not sum/average/min/max values, compute success rates or metric summaries, compare tracks/policies, calculate a digest, validate a qualification condition, or transform records into a status used by any other component. The UI must visibly label this view **“device v2 replay · human display only · not evaluation or qualification evidence.”**

Hard isolation rules:

- The v2 reader is read-only, non-authoritative UI. Its output cannot feed training, policy selection, evaluation calculations, evaluator report validation, campaign scheduling/sealing, curriculum state, qualification/promotion, readiness, manifest validation, checkpoint choice, PPO replay verdict, or any existing metric/comparison/qualification panel.
- Do not alter the current `/api/meco-status`, `/api/curriculum-status`, three-pass provenance calculation, comparison summaries, qualification objects, or their consumers to consume v2 display output. Keep the current v1 JSON/replay readers intact for historical artifacts; never relabel v1 as v2 or v2 as v1.
- Do not write a dashboard v2 projection/summary/sidecar/cache. Serve v2 response with `Cache-Control: no-store` and frontend fetch `{cache:"no-store"}`. Avoid in-memory parsed-result caches; timeline paging may select a byte/record range but cannot precompute rollups.
- Do not compute/verify SHA-256 or any other digest over a v2 record, decoded values, or display JSON in dashboard code. The producer may include its device-created record digest and run/source/checkpoint/protocol bindings; the dashboard displays these verbatim and clearly labels them producer claims. File safety and static envelope/schema/size checks do not authenticate dynamic contents. Any integrity/authentication requirement belongs to the producer/campaign owner and must not be implemented as a dashboard hash.
- The browser may render v2 data only in the isolated replay pane, not by mutating the normal status/comparison model. Selecting a v2 replay must not update three-pass validation status, current qualified candidate, metric summaries, or readiness badges.

## Provenance, replay binding and three-pass behavior

The viewer consumes only fields, identities, and bindings explicitly defined by the accepted shared ABI and exact accepted PPO producer-envelope schema. It must not require, rename, synthesize, or add producer fields from this dashboard plan. Where the accepted schema defines them, display static source/runtime/config/checkpoint/protocol identity, track/schema, rollout/episode slot, and replay/scenario/seed metadata as recorded. Keep policy-local and source-global candidate/support row IDs as separate producer fields. A source/checkpoint/protocol mismatch may be shown as an explicit **displayed mismatch** annotation; it cannot be converted to a pass/fail qualification or campaign state. Malformed, incomplete, oversized, mutable, unsupported-schema or unbound envelopes fail closed with a user-visible display error and no fallback to a stale v1 projection.

Keep the existing replay-generation source binding behavior for v1 unchanged. The v2 reader must resolve only the canonical producer-published v2 replay referenced by its ready pointer / record ID, keep the returned record tied to that generation and its embedded source/checkpoint/protocol IDs, and use no-store responses. Do not derive the binding by hashing or rebuilding a Python JSON projection. The producer-owned v2 schema must specify immutable generation/pointer semantics and its device-produced identity; if current `dashboard-replay-generation-v1` host-generated asset hashes cannot represent this, add a separately versioned v2 generation contract in the upstream artifact owner first. The dashboard cannot make its own manifest or digest to bridge the gap.

Preserve `dashboard_api.py::_three_pass_provenance()` and the current `meco-three-pass-provenance-v2` validation path, including its pinned summary-only planner/implementer/reviewer fields, exact commit/artifact links, and trust/error statuses. The existing three-pass panel remains sourced from the checked-in provenance manifest and `/api/curriculum-status`; the v2 replay pane displays its separate device-record provenance as unverified producer metadata. Never let v2 record fields replace, upgrade, or downgrade the validated three-pass object. Preserve the current dashboard behavior when three-pass provenance is untrusted.

## Acceptance and runtime gates

**Pass 2 contract tests (synthetic record fixtures):**

1. A valid producer-shaped v2 record renders the exact recorded timeline and values; policy-local/global IDs, selected/executed action, route/goal and per-tick statuses remain distinguishable. Unknown/missing schema, corrupt field layout, invalid path, symlink, over-limit size, missing required provenance, stale generation pointer and malformed bytes fail closed.
2. V1 artifacts remain readable exactly as before. V2 data never enters or changes `/api/meco-status`, `/api/curriculum-status`, three-pass provenance, comparison metrics, qualification, readiness, campaign or validation-runner results. Tests assert no call into `_comparison`, evaluator validators, or qualification/campaign functions from the v2 display route.
3. V2 dashboard code performs no record digest, no dynamic aggregation/metric calculation, no status promotion and no persistent/in-memory projection cache. Endpoints and browser fetch use `no-store`. Producer-provided source/checkpoint/protocol/replay identity is rendered unchanged and mismatch is visibly annotated only.
4. A fake HTTP/dashboard handler and static asset checks prove the v2 view is actually reachable and human-readable while current status/three-pass panels continue using their existing source. These tests do not establish runtime currentness.

**Required future end-to-end simulator/replay validation:** after the associated device command, transition, simulator and producer record implementations are independently accepted, physically attested WX9100 leases are released, and the relevant code is integrated, run seeded simulator scenarios exercising the changed v2 records for A1, A2, A3, C1 and C2. Include legal/executed action identity, C policy-local/source-global row mapping and continuation, A global/local support identity, goal/route, remask/fallback/preemption, gamepiece event/reward/terminal and replay-frame binding. Retain scenario, seed, run/replay ID, source/checkpoint/protocol identities and inspected result. This plan does not authorize or perform that work.

Before any fresh replay is generated or reviewed, follow `AGENTS.md`: restart the dashboard backend from the exact reviewed checkout; verify active service PID, workdir and commit; verify `/api/meco-status`, `/api/curriculum-status`, the v2 display endpoint, and every relevant frontend asset (`/`, `/meco`, `dashboard.css`, `dashboard.js`, `meco.css`, `meco.js`, `field_rendering.js`, `training_rendering.js`) against that checkout by byte/hash comparison; ensure three-pass provenance is current and clearly separate from v2 producer metadata; then generate a fresh replay and inspect it in the v2 human view. Mark replays produced by old code or an earlier service process outdated. Report scenario, seed, replay ID, source/checkpoint/protocol bindings, service identity, endpoint results, frontend asset hashes, and inspection outcome. If a required process, endpoint, asset, replay or provenance check is unavailable, report the gate incomplete. A v2 human display is never qualification evidence.

## Nonclaims and stop conditions

This Pass 1 document does not claim that v2 records, a parser, a UI, a current dashboard, a successful simulator, training, or qualification currently exist. It neither authorizes tests/runtime nor weakens the whole-compute boundary outside the single human-display-only reader. Stop if the output schema is not canonical and producer-owned; if rendering needs host hashing, aggregation, or numeric acceptance logic; if the reader touches a gate/status/cache; if a v1 artifact would be presented as v2; or if local/global row, command, transition and source/replay identities cannot be shown exactly as produced. Do not infer v2 validity from displayability.
