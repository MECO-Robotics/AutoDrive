## Objective and operating boundary

The source plan's primary decision is whether each learned architecture improves held-out match outcomes over the strongest fair deterministic control without increasing safety violations. The evaluation must retain these five tracks as separately trained and reported approaches:

- **A1:** multiscale CNN U-Net + GRU, dense legal-pose `U/P` and behavior logits.
- **A2:** structured SE(2) U-Net + regional attention + GRU, dense legal-pose `U/P` and behavior logits.
- **A3:** hierarchical SE(2) GNN + regional attention + GRU, per-node `U/P` and behavior logits.
- **C1:** candidate-feature MLP + GRU, candidate strategic utilities.
- **C2:** map encoder + candidate cross-attention + GRU, candidate strategic utilities.

Use the same frozen train/calibration/validation/final-test partition, scenario tuples, observation contract, opportunity set, safety constraints, and evaluation budget for all five. Report Plan A's dense routing outputs and Plan C's candidate ranking with their real runtime/feature-extraction costs; do not silently normalize away their different action spaces. D0 remains the pinned production deterministic policy. D1 and both supported D2 prediction variants remain explicit matched controls. Predeclare the comparator set and deterministic control-selection rule before looking at calibration outcomes. Do not choose a favorable comparator, margin, or scenario after examining held-out results.

The user-requested continuous r4 campaign is diagnostic and belongs to an older checkout. Do not stop, reconfigure, checkpoint-migrate, relabel, or otherwise disturb it. Do not run a competing simulator, calibration, or training job while it holds the WX9100 leases. After the user manually stops it and both devices are actually released, any subsequent training and simulator/calibration work must use the two WX9100 devices, explicitly indexed, with CPU fallback disabled. A device lease or status file alone is not proof that a device is free. Offline source review and pure contract tests do not consume the simulators or qualify runtime results. Nothing here authorizes GPU/device use or a training launch.

## Blocking semantic prerequisite: authoritative match outcome

Before calibrating or promoting, audit the source plan's match-point-contribution endpoint against the simulator's actual scoring implementation. Add or identify a deterministic, source-versioned score-accounting layer that derives the episode outcome from authoritative simulated game events and frozen scoring rules. The record must distinguish official/simulated match points (including any enabled bonuses, penalties, or terminal conditions) from raw FUEL-piece count, useful throughput, policy-attributed contribution, and team score. Record the event ledger and the scoring schema/version used so a replay can independently reproduce the result.

Do not write FUEL counts, throughput, proxy rewards, or dashboard counters into a `match_points` field. Do not label an outcome “official” unless the implementation faithfully models the relevant game rules. If the simulator does not contain enough rule/event information to calculate the source plan's primary outcome, report that gap and keep the v5 gate blocked until the scoring model is completed and independently reviewed. A human may approve an explicitly scoped simulated match-outcome definition, but that definition must be specified before data collection and may not masquerade as official FRC scoring.

## Ordered implementation and evidence passes

### Pass 1 — scoring semantics and executable source freeze

1. Trace score events from simulator event production through `meco_metric_ledger`, evaluation rows, report intake, and replay records. Create a field-to-source map for official/simulated match outcome, per-team totals, robot-attributed outcomes where valid, score penalties, safety rates, and terminal state. Preserve the existing scored-FUEL semantics as a separate field.
2. Implement and review the versioned match-outcome accounting and replay reconstruction seam described above. Add mutation cases for missing, duplicated, reordered, or inconsistent events; altered scoring rules; replay/report disagreement; and attempts to substitute throughput or FUEL count for outcome points. Do not proceed to outcome calibration until the reviewer accepts this contract.
3. Use the existing freeze-v2 compiler only after gathering the actual effective configuration for a clean, pinned source/runtime. Bind the eight required configuration IDs and exact content hashes; record explicit values/hashes for robot dynamics, geometry/connectivity, opponent schedule, action cadence, sensor noise, scoring semantics, and safety semantics. No prose-only attestation, inferred default, dirty source tree, or old r4 checkpoint can satisfy the freeze.
4. Compile the four disjoint train/calibration/validation/final-test partition artifact using source-plan held-out defender families, layouts, and start conditions. Verify tuple-level and axis-level non-overlap, all five model assignments, and final-test single-use restrictions. Preserve the existing v1 protocol and historical v2–v4 artifacts as read-only legacy evidence; do not retrofit them with a later freeze.
5. Bind future training manifests and all five track checkpoint bundles to the exact freeze, partition, source commit/tree, dependency lock, backend, and campaign IDs. Reject checkpoints from r4 or any different source/protocol. The output of this pass is a new eligible-to-collect protocol candidate, not an executed freeze or qualification.

### Pass 2 — resumable, paired D0/D1/D2 calibration

1. Extend the existing D0 shard coordinator contract rather than creating a second incompatible campaign format. Add immutable matched-reference manifests, receipts, resume, and merge for every predeclared deterministic control: D0; D1/current; D2/cv; and D2/multi_model_v1 where that variant is part of the preregistered control set. Each shard binds the same exact case/category/stratum/layout/defender/start/sensor/seed/repetition tuples, baseline freeze, partition, source, scoring schema, protocol, normalized runtime, predictor identity, candidate K/route-cost settings, and exact indexed device identity.
2. Assign shard work to the two visible WX9100 devices with one explicit accelerator per worker, no `cuda` auto-selection and no CPU fallback. Merge may accept the two device UUIDs only when each shard proves the expected WX9100 model and identical backend/software/runtime contract; preserve per-shard device identity. Fail closed on a P600, CPU, mixed backend/version, missing device identity, or runtime drift. Do not hold a device while waiting on manual intervention.
3. D0 and each D1/D2 control must execute the same calibration tuple and scoring/accounting semantics. Include repetitions for within-seed variance and distinct calibration seeds for between-seed uncertainty. Define completeness from the frozen schedule; never hardcode a historical record count if the registry or strata change. A scheduler description is not runtime evidence.
4. Extend raw report, shard, and bundle schemas to require replay-bound match-outcome records and all three safety rates, with raw-event digest, scorer/schema identity, outcome and team attribution, condition/control policy, exact seed/repeat, source/runtime/protocol, and stable bundle digest. Keep throughput, navigation, and other source-plan metrics as secondary fields. Reject missing or inconsistent outcome/replay, duplicate or overlapping work, partial scenario closure, stale source, altered rows, incomplete repeat coverage, leaked partition tuples, and unregistered control variants.
5. Produce immutable complete bundles for each preregistered deterministic control and a calibration summary of paired outcome differences, between-seed and within-seed variance, confidence intervals, and safety rates. A retry may reuse a shard only after its bytes and all identity fields validate exactly. No report from `pickup_simple` can stand in for full-closure evidence.

### Pass 3 — human margins, v5 protocol, and five-track evaluation handoff

1. After complete calibration bundles are reviewed, create a human-authored immutable margin-review artifact bound to their exact digests and the frozen baseline/protocol. Record the primary match-outcome estimand, comparator-selection rule and result, target scope, minimum operationally useful gain and rationale, confidence-interval method, and separate non-inferiority margins for robot, field, and wall contact rates. Make the primary promotion gate the paired held-out match-outcome difference for each of A1/A2/A3/C1/C2 against the predeclared strongest eligible deterministic control, meeting the human-reviewed useful-gain threshold and confidence rule. Require every safety-rate paired interval to satisfy its own non-inferiority margin. Throughput, FUEL count, navigation, robustness, calibration, compute and latency remain secondary and cannot override primary or safety failure. Report each track independently; a five-track aggregate cannot conceal an individual failure or missing track.
4. Carry the protocol into Phase 2 data collection, supervised warm-start and RL manifests without excluding an architecture due to convenience. Continue to keep Plan A `P` targets at P0 unless independently supported labels exist; do not infer that Phase 0 protocol completion creates training data or weights.

Update `MECO_FULL_PLAN_EXECUTION_STATUS.md` to separate implemented contracts, generated artifacts, simulator evidence, and qualification status.

## Independent three-pass workflow and commit boundaries

For each implementation tranche, use separate scoped planner, implementer, and independent reviewer roles. The implementer works from the approved exact plan head in an isolated worktree and commits/pushes coherent changes incrementally. The reviewer checks the exact pushed candidate head and its acceptance evidence; a code-only approval cannot approve runtime or outcome claims. Integrate only after the exact-head review passes. Preserve the unrelated HIP kernel edit in the root worktree.

Recommended independently reviewable tranches are: (a) score accounting and replay binding; (b) actual freeze/partition production handoff and manifest binding; (c) matched D0/D1/D2 resumable campaign plus strict merge; (d) match-outcome/safety report intake and margin review; (e) v5 protocol and five-track evaluator handoff. Update three-pass dashboard provenance after each integrated tranche, then restart the dashboard from the current checkout and verify both current backend and frontend hashes before presenting dashboard evidence. This dashboard check is not a substitute for simulator replay review.

## Acceptance criteria

- The primary endpoint is derived from an authoritative, versioned simulated match-scoring ledger, reconstructable from the exact replay. Raw FUEL counts, throughput, and proxy reward are never promoted as match points.
- A clean source/runtime-bound freeze and disjoint four-way partition are generated from effective configuration values; all five model manifests bind them. The active diagnostic r4 campaign remains unbound and untouched.
- D0, D1/current, D2/cv, and D2/multi_model_v1 controls named in the frozen preregistration have complete resumable paired calibration over the full frozen scenario/stratum/seed/repetition schedule, with immutable raw records, scorer/replay provenance, runtime/device identity, safety metrics, and merged digests.
- Two explicit WX9100 devices execute eligible simulator workloads with CPU fallback disabled; no P600 or CPU result enters calibration/training evidence. Work waits for the user's manual stop of r4 and natural release of both devices.
- A reviewer-approved, human-authored margin artifact binds exact calibration bundle digests. No operational margin is auto-selected from observed variance.
- v5 gates each of A1/A2/A3/C1/C2 on preregistered paired held-out match outcomes and safety non-inferiority. Final-test tuples are isolated and consumed once. v1–v4 remain historical/read-only and cannot qualify current models.
- Full-plan status explicitly distinguishes code support, checked-in plans/configuration, generated datasets/checkpoints, seeded end-to-end simulator evaluations and inspected replays, held-out outcomes, deployment profile, and qualification. No phase is described as complete based only on update counts, unit tests, or dashboard state.
