## Why this is the next shared blocker

The shared PPO update in `frc_defense/meco_track_training.py::_ppo_update` is called by `train_meco` for A1, A2, A3, C1, and C2. The current implementation builds tensor stacks but then reads row metadata in Python, tests a device mask with `bool(actor_rows.any())`, transfers the device permutation through `order.tolist()`, performs one optimizer update per row, and accumulates diagnostics through host scalar conversions. `_gae` is a Python reverse loop over the trajectory. Rollout records are Python dictionaries assembled in `train_meco`; selected actions are materialized for environment dispatch. The exact transition between allowed final action dispatch and forbidden host-derived training control is not yet a single versioned, enforced device contract.

`docs/plans/phase3-plan-a-ppo-replay-contract-tests-20261025.md` proposes offline Plan A replay contract tests, not a device-resident optimizer implementation. The whole-compute GPU plan describes the required endpoint but does not provide a scoped PPO implementation tranche. This plan fills that shared Phase 3 gap only. It does not claim that the five tracks can train end to end now: route/candidate, observation/snapshot, simulator physics, bootstrap, Phase 0, Phase 2 data/warm starts, and other currently planned prerequisites remain independently blocking.

## Required numeric and behavioral invariants

1. **All five architectures use one contract.** `track` chooses only the existing model/policy interface and frozen A/C support type. The common PPO batch, GAE, optimizer, and RNG semantics apply identically across A1/A2/A3/C1/C2; no architecture may fall through to the old per-row numeric implementation in qualifying execution.
2. **Device is authoritative.** Every numeric transition field, policy output, sampled action index, old/new log probability, value, reward/terminal flag, actor eligibility, advantage, return, permutation, transition gather index, loss, gradient norm, optimizer state/update, replay equality predicate, and finite/overflow check remains on the explicitly attested indexed WX9100. Device scalar reads, `.item()`, `.tolist()`, `.cpu()`, NumPy conversion, Python booleans, and host reductions cannot control replay acceptance, row eligibility, sample ordering, optimizer work, update count, or success/failure.
3. **Only final interface payloads cross the boundary.** Environment command dispatch may receive the already-selected compact action payload after selection is final. Serialization may receive an opaque completed artifact or passive numeric diagnostics after the update has completed; it cannot reconstruct the training batch or alter continuation, row inclusion, loss, optimizer state, or qualification/readiness. Any dynamic diagnostic needed to assert validity must be decided in device code and returned as a typed pass/fail status.
4. **PPO semantics stay unchanged.** Preserve stochastic masked categorical distributions, support/candidate row identity and order, action/log-probability pairing, clipping, entropy and value coefficients, critic-only handling for execution failures, terminal/truncation bootstrap behavior, normalization population and epsilon, gradient clipping, shuffled single-transition SGD order and one optimizer step per eligible transition slot, update scheduling, learning-rate behavior, and current per-track model/optimizer parameter coverage. A semantic change requires a separately reviewed experiment and new protocol/source identity.
5. **Replay checks remain pre-mutation.** Frozen A support and C candidate/route/risk/replay inputs must be validated against the rollout's exact selected index and log probability before the first optimizer update. A failed device verdict aborts the entire PPO update; it cannot accept a partial batch or leave partially updated weights.
6. **RNG and resume are reproducible.** Define the generator/device ownership and serialized state for action sampling, minibatch permutations, model initialization, and continuation. Checkpoint/resume must preserve the exact next minibatch/action sequence and optimizer state. Host CPU RNG or Python row order may not determine training numerics.
7. **No implicit qualification.** A completed PPO update, finite loss, training counter, or passing tensor test means only that this isolated update path ran. It does not establish simulator behavior, five-track source integration, Phase 0/2 readiness, evaluation success, stage-1 qualification, or whole-compute GPU-only compliance.

## Explicit exclusions and integration dependencies

- **Excluded adjacent plans:** candidate membership/expansion/commitment and scoring (`gpu-candidate-eligibility-fallback-tranche-20261026.md` and the separately reviewed candidate work); observation/sensor, state snapshots, planner and reset predicates (observation preprocessing plan); FUEL/gamepiece/robot simulator physics (`gpu-simulator-gamepiece-physics-tranche-20261026.md`); bootstrap statistics and promotion gate (`three-pass-v4-gpu-bootstrap-ledger-dashboard-20261026.md`). This plan must not edit or silently accept those boundaries.
- **Five-track path dependencies:** the device-native A support and C candidate/score paths must be integrated and exact-head reviewed before a qualifying PPO run. Batch adapters must consume those frozen contracts without host reconstruction. The observation and physics device plans must separately pass parity and required seeded simulator evaluation before training behavior evidence is meaningful.
- **Supervised fitting dependency:** this does not move Phase 2 U/B/P or C dataset fitting, target construction, train-case closure, or warm-start validation to device. Use the approved Phase 2 plans for data and warm starts. No optimizer run from this tranche substitutes for a source-bound complete five-track warm-start set.
- **Evaluation/qualification dependency:** policy evaluation metrics, paired inference, confidence intervals, score ledger, held-out protocol, qualification and promotion are excluded. Keep them governed by the Phase 0, Phase 4 and bootstrap plans. This tranche cannot authorize a training campaign.
- **Campaign constraint:** do not stop, pause, resume, configure, attach evaluation to, or otherwise mutate any active or historical campaign. Do not touch checkpoints, logs, device lease records, service state, manifests, protocol data, or campaign output roots.

## Acceptance evidence for the future implementation

- Source inspection shows no device-derived host synchronization or host value controls PPO row inclusion, GAE, masking, replay verdicts, minibatch order, loss, optimizer updates, update counts, RNG progression, or failure handling for any of A1/A2/A3/C1/C2.
- Device fixtures match the frozen reference for all five tracks on terminal/truncated sequences, support/candidate masking, action log probability, GAE, clipped objective, critic-only failures, partial-rollout capacity masks, exact shuffled per-transition optimizer order, gradient clipping, optimizer state, and checkpoint/resume next-step determinism.
- Pre-update invalid-input fixtures prove no model or optimizer state is changed on a rejected batch. Unsupported device, malformed schema, non-finite values, capacity violations, or replay mismatch return an explicit fail-closed result.
- Device traces/instrumentation on verified WX9100 hardware show PPO tensors, permutations, comparisons, reductions, gradients, and optimizer updates stay on-device. Passive report serialization is proven not to gate an update.
- A later integrated behavior evaluation follows project `AGENTS.md`: reproducible scenario and seed, fresh replay inspected for the changed path, dashboard current checkout/backend/frontend verified, and result retained. Tests alone do not satisfy this gate.
- Exact implementation head, focused test outcomes, physical device/lease identity, simulator scenario/seed/replay, and dashboard currentness are reported separately. No evidence is presented as completion of five-track training, evaluation, stage-1 qualification, or whole-compute GPU-only readiness unless every separate dependency gate passes.

## Stop conditions

Stop and revise this plan if the implementation needs to change policy/action semantics, candidate/support membership, simulator transitions, observation contents, reward/score definitions, Phase 0/2 authority, evaluation aggregation, or qualification thresholds; if fixed-shape batch execution changes optimizer/update cadence without an approved semantic version; if any numeric predicate or failure path must be read by host to continue; if model/optimizer/checkpoint state cannot be resumed reproducibly on the declared device; or if physical device identity/lease or required independent review cannot be established. No CPU numerical fallback or weakened test/qualification gate is permitted.
