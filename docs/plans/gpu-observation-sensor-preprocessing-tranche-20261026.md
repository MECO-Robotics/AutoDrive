# Pass 1 plan: GPU-resident observation and sensor preprocessing

**State:** implementation plan only; static source review, no code/runtime changes.  
**Reviewed base:** `53f3d9c9a49a7e12bf65b5e1fa2797f4464e63be`.  
**Execution constraint:** the live diagnostic r4 campaign remains untouched and uninterrupted. Defer fixtures, GPU/device checks, profiling, and simulator evaluation until r4 is manually stopped and both WX9100 leases are released.

## Objective and boundary

Make the simulator observation and sensor-preprocessing data that feeds policy inputs GPU resident from active-world selection through perception/tracking, observation assembly, normalization, and the returned observation tensor. Device masks and tensors must determine all per-world/per-robot work. No CPU read of a tensor predicate may branch, compact, choose, or alter policy-visible values.

This tranche covers `_tensor_3v3_observation` active-world sampling/branching, the `observation.py` NumPy normalization adapter, `tensor_3v3.step`, `tensor_defense_step.step`, `tensor_physics.TensorSim.step/_step_eager`, active-count and active-nonempty producer/caller contracts, `tensor_defense_reset.reset_done`, and `tensor_sim.py`/`tensor_defense_observation.py` perception and observation callsites feeding policies. Candidate generation/scoring and PPO optimization/update math remain separate. The narrow trainer-runtime boundary is included only to audit `_active_count` producers and ensure they do not copy device predicates to host; broad PPO trainer-loop restructuring remains separate. Static configuration such as robot roles, fixed capacities, and field dimensions may remain host metadata; values read from runtime device masks may not drive host control flow.

## Source callchains in scope

1. **3v3 policy observation:** `tensor_3v3.py::reset/step` → `_tensor_3v3_observation.py::_update_perception` → sensor detections, anonymous tracking, and opponent tracking → `observe(active_mask)` → `[world, robot, 137]` observation tensor. This is the primary six-robot policy observation path.
2. **Defense/strategic observation:** `tensor_defense_step.py::step` → `tensor_defense_observation.py::_update_perception`, `_raw_obs`, `_strategic_observation`, `_obs` → policy observation history and current state. Include `tensor_defense_reset.py::reset_done`, where `bool(mask.all().item())` controls planner cadence. Maintain active masks and cache/history merge semantics.
3. **Normalization:** `observation.py::normalize_numpy_observation_in_place` is a separate NumPy path; `normalize_tensor_observation_batch_in_place` is the torch path used by both observation mixins. Policy-facing normalization must use a device-resident tensor implementation with the same fixed scales and clamps.
4. **Sensor kernels and observation prototypes:** `tensor_perception.py`, `tensor_strategic_observation_proto.py`, and `tensor_strategic_observation_full_proto.py` are called from the above paths. Keep their observation-visible intermediate tensors on the selected device; any optional extension/prototype selection must be static capability/configuration, not a data-dependent host predicate. If an extension cannot satisfy the device contract, fail closed for the GPU-only qualifying path rather than silently switching to a host observation implementation.
5. **Active-count boundary:** audit `tensor_3v3.step` and `tensor_defense_step.step`, their `_active_count` arguments, and every caller. In particular, inspect `tensor_training_runtime.py` (known horizon schedule, `remaining_ticks.detach().cpu()` reduction, and fallback `active_this_decision.sum().item()`) and `tensor_training_evaluation.py` (`active_episode_count` is scheduler-known and forwarded for strategic calls). Remove any device-mask reduction/copy used to choose host branches; caller-provided counts are permitted only when already known as static/scheduler shape metadata, otherwise retain the full device mask and use fixed-shape masked tensor operations. This does not authorize unrelated PPO optimization changes.
6. **Physics active-mask boundary:** both policy step paths call `advance_with_fuel` and then `env.sim.step`. `TensorSim._step_eager` currently checks `bool(active_mask.any())` for an early return unless `_active_nonempty` is asserted; audit `tensor_3v3.step`'s `active_count>0` producer and all `advance_with_fuel` forwarding/default/graph-capture callers. This hint may be trusted only when supplied as host-known shape/scheduler metadata; it cannot be derived from a device mask. Prefer fixed-shape physics work with device-masked state updates so empty and partial masks preserve exact semantics without a host predicate.
7. **Policy handoff:** `env.observe()` and `_obs()` return device tensors consumed as `_last_obs` by policy decision code. This tranche ends at that tensor boundary. Action selection, candidate construction/scoring, and PPO update math are outside scope.

## Current issues to resolve

- `_tensor_3v3_observation.py::_random_active` computes `int(active.sum().item())` when `active_count` is absent, then uses that host count to allocate a compact random tensor. This creates a device synchronization and a data-dependent host branch. The active mask must remain a device tensor; random draws and masked writes need a GPU-only design.
- `tensor_3v3.step` computes `active_count` with `int(active.sum().item())` when `_active_count` is absent, and its later sensor-update path computes `int(update_active.sum().item())`. `tensor_defense_step.step` similarly extracts `int(active_mask.sum().item())`. These counts control early returns, planner full-batch modes, perception sampling, and observation paths. Replace these with device-masked/fixed-shape behavior; do not repair only `_random_active` while leaving step-level host predicates.
- `_obs` and 3v3 `observe` include Python branches such as partial-batch checks and first-frame logic. Represent runtime decisions as tensor masks/selects; use only caller-known static initialization metadata for unavoidable shape branches. Do not call `bool(active.all())` or materialize a device predicate for host control flow. `tensor_defense_observation.py::_random_active` also extracts `.sum().item()` when no count is supplied. Remove this fallback; fixed-shape draws and device masking must support the no-count path.
- `observation.py::normalize_numpy_observation_in_place` has host scalar/list arithmetic, and may be used by NumPy adapters. Keep it for explicit offline/CPU compatibility if necessary, but exclude it from qualifying GPU policy paths. GPU validation must prove the active policy callchain uses only the tensor normalizer.
- `tensor_physics.TensorSim._step_eager` uses `bool(active_mask.any())` for a host early return. On the five-track callchain, `tensor_3v3.step` passes `_active_nonempty=active_count>0` through `advance_with_fuel` to `TensorSim.step`; because the count can itself be mask-derived this does not remove the predicate. Other `_active_nonempty` callers include `advance_with_fuel` forwarding its hint to eager steps and its graph capture, plus `TensorSim.step` compile-path internal assertions. Eliminate tensor-derived early return/claims, and ensure empty/partial masks retain the exact physics state-update semantics using device masks.
- `tensor_defense_reset.py::reset_done` computes `full_reset=bool(mask.all().item())`, then uses that host predicate to restore scalar planner cadence. Migrate this path too: preserve per-world reset semantics with device state/masks or a separately supplied caller-known reset mode; a tensor mask may not be copied to decide whether scalar fast-path state changes. If the scalar optimization cannot be kept GPU-resident, disable it for this path and use the per-world tensor cadence.
- The observation/perception code contains static Python branches over configured control modes/roles and feature availability, plus host flags returned by optional kernels (`fused_tracks`, `fused_opponents`). Classify each: static configuration/capability branching can remain; runtime tensor outcomes must be applied through device masks and cannot decide host execution or skip required work. Existing CPU-specialized visibility paths must not be used by qualifying GPU execution.

## Device-resident shape and control contract

- Active worlds: boolean tensor `[N]` on `env.device`; every update is masked with this tensor. No `active.any/all/sum`, tensor-to-bool conversion, `.item()`, `.tolist()`, `.cpu()`, or NumPy conversion may control a host branch in the qualifying path.
- 3v3 observation output: floating tensor `[N, 6, 137]` on `env.device`; `OBS_DIM=137`. Row updates and preservation of inactive worlds use tensor `where`/masked writes.
- Sensor visibility and anonymous detections: device masks such as `[N, 6, F]` or configured camera-expanded forms; positions/velocities `[N, 6, F, 2]` (or their documented camera/observer-expanded tensors), with validity, confidence, extents, and merge markers aligned on the same device.
- Track state: bounded position/velocity `[N, 6, F, 2]`, age/confidence/validity `[N, 6, F]`; opponent estimates `[N, 6, ...]`. Association, one-to-one collision resolution, stale-track expiration, and active-world commits must be tensor operations on `env.device`.
- Defense raw observations: fixed schema batches `[N, 35]` or the configured strategic width, normalized in place by the tensor normalizer. History writes/merges use device indices/masks and preserve inactive rows.
- Configuration values (e.g. fixed robot count, static mode tuple, field extents, model capacity) may be host scalars. `_active_count` may remain only as known shape metadata already available from a static scheduler contract; audit all callers and prohibit deriving it from a device mask, including `.sum().item()` or `.detach().cpu()` reductions. No-count paths must remain correct using fixed-shape draws and device masking. Step early-return/full-batch behavior must not branch on a count derived from runtime tensors.
- Preserve sensor RNG determinism as an explicit contract. If fixed-shape device draws change random consumption relative to compact active-only draws, version the observation/runtime identity and regenerate compatible seeded fixtures after device release; do not silently claim seed parity.
