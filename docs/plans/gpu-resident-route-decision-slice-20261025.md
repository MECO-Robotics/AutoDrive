## Why this is the next slice

The evaluator used by Plan C already builds occupancy grids and runs `TensorADStar` with tensor state, but `evaluate_routes` then enumerates device masks with `.tolist()`/`.item()`, copies every path and cost map to CPU, performs per-route endpoint and weighted-cost work in Python, and returns `RouteResult` objects with Python floats and point tuples. `build_route_feasible_candidates` consumes those objects to build Plan C features. The live C1/C2 caller later materializes route values back into tensors; `_d1_d2_scores` also reads route/risk tensors one scalar at a time before rebuilding device logits. This places repeated synchronization and host computation directly between route planning, candidate scoring, and action sampling.

The slice covers the **Plan C numeric candidate, route-result, policy-input, selection, command, and V3 evidence path**. Host may prepare immutable schema/configuration and a static ordered candidate-template description, but may not construct observation-dependent candidate rows, query geometry, dynamic IDs/indices, features, route inputs, or per-candidate Python objects. Raw transport/configuration I/O may remain host-side; observation decoding, tracking, feature formation, and numeric input preparation must follow the whole-compute device contract and are not granted a CPU-compute exception here. Numeric route/candidate values and their stable integer identities remain tensors on device. The selected device command flows directly to the native simulator consumer; command, execution, and transition evidence is written to the canonical V3 row and device-produced opaque record bundle. Host may persist opaque bytes unchanged; it may not project, decode, reformat, hash, aggregate, or inspect dynamic evidence. Plan A support construction remains a separately owned Plan A tranche and must use the same ABI when integrated.

### Residual work outside this tranche

This slice addresses the Plan C route-decision portion of the user's GPU-only objective. The work below is not performed by this tranche, remains governed by the whole-compute plan and its owner tranches, and is **not permission for CPU numerical computation**:

- **Plan A:** legal pose-graph/support construction and Plan A scoring/selection are separately owned; they must satisfy their accepted Plan A scope and shared ABI before a five-track implementation can integrate.
- **Static candidate template:** immutable schema, configured slot order, and static identity dictionary setup may be prepared as host metadata. Dynamic candidate/query values, IDs, row maps, actions, goals, and validity remain device-produced and device-consumed.
- **Perception and extraction:** raw transport and configuration I/O may use the host. Numeric observation decoding, object/track extraction, association, feature formation, and dynamic device inputs are covered by the whole-compute plan and must be moved/validated there; this route slice does not make them CPU-compute allowances.
- **Simulator and dispatch:** command consumption, safety predicates, state transitions, and action execution in a qualifying path must be device-resident under the shared ABI and simulator owner plan. This plan does not implement their kernels, and it authorizes no host action dispatch bridge.
- **Orchestration and learning:** process scheduling, device/lease coordination, kernel launch, IPC, and file/network I/O are host orchestration. PPO/training/fitting/evaluation numerics and dynamic status/metrics are device work under their owner plans.
- **Serialization:** device-generated V3 evidence is an opaque byte bundle. Host file/network I/O may move those bytes unchanged; numeric report/replay projection, hashing, aggregation, and decoding require separate approved device/display contracts.

No other project phases or gates are closed by this plan.

## Required vertical slice

Add a typed `DeviceCandidateBatch` and fixed-capacity/chunked `DeviceRouteBatch` for the existing candidate and route-query order. Their numeric fields must live on `env.device`:

- `status_code` and `feasible`: one entry per input query; invalid, at-goal, no-path, and feasible states remain distinct.
- `path_xy` and `path_length`: padded `[Q, MAX_ROUTE_POINTS, 2]` coordinates plus device lengths. Preserve the current AD* route point order and start-escape segment.
- `distance_m`, `endpoint_error_m`, and `weighted_cost_grid_edges`: device scalars per row. Integrate learned and bump costs at the same raster-boundary interval midpoints and preserve normalized cardinal-grid-edge units.
- `candidate_index`: `int64[Q]` query ordinal in canonical query order, not a source-global row or candidate identity. Include the shared ABI's `route_query_row_map:int64[Q]`, `route_query_variant:int64[Q]`, `route_query_active:bool[Q]`, `route_query_world:int64[Q]`, `route_query_robot_slot:int64[Q]`, and `route_query_generation:int64[Q]`. Each result is bound to the exact source-global candidate row and snapshot on device; no row map, dynamic identity, or selection scalar is transferred to Python.
- Use the accepted ABI route profile exactly: `Q<=64` per call, `P=73`, `status_code:int64[Q]`, `feasible:bool[Q]`, `path_xy:float32[Q,73,2]`, `path_length:int64[Q]`, `path_point_mask:bool[Q,73]`, and `distance_m`, `endpoint_error_m`, `weighted_cost_grid_edges:float64[Q]`. Optional bump/learned component costs are `float64[Q]` with static presence/provenance codes. Preserve its inactive-row, padding, finite-value, source mapping, and device-validation rules; do not define a competing route schema.
- For a static total query count above 64, use host-known fixed integer chunk spans and preserve their order; each chunk result remains on-device and results are concatenated/reassembled on-device. `candidate_index` is query-local within a call and global query ordinal across the concatenated table; `route_query_row_map` always maps to the source-global candidate row. Do not compact queries based on device outcomes or read row maps on host.
- Keep static candidate/action schema and identity dictionaries separate from dynamic tensor columns. Candidate action, target identity, goal/heading, route override, and validity columns are device values gathered using the source-global row mapping; static host metadata may initialize fixed schemas but cannot be consulted using a device-selected value.
- `ordinary_features`: schema-20 feature values plus missingness indicators, `[1,K,40]`; `ordinary_valid_mask:bool[1,K]` and `ordinary_row_map:int64[1,K]` bind the ordinary K-prefix to source-global rows.
- `continuation_features`: separate `[1,K,40]` query view containing the optional continuation only at local slot 0; `continuation_query_mask:bool[1,K]` and `continuation_row_map:int64[1,K]` use sentinel `-1` for inert slots. Its local slot 0 maps to the existing source-global `continue_index`; it does not consume or replace an ordinary slot.
- Both views preserve the exact schema-20 raw feature order, matching schema-20 missingness indicators, and unavailable-value meaning. Keep policy views separate from expanded route-oracle candidates used only for recall. The C2 continuation query uses the same already-computed ordinary-prefix recurrent context; it must not alter that context or run the GRU again. Apply all mappings and masks on-device.

The accepted shared command/transition ABI is normative. Its route result is the device tensor batch above; do not project a live `DeviceRouteBatch` to `RouteResult`, Python tuples, numeric report fields, or decoded host evidence, either before or after selection. A CPU-compatible reference may be used only as a separately constructed test oracle, never as projection of live device results or a production fallback. C1/C2 scoring and any retained D1/D2 comparator scoring consume device candidate, feasibility, route, and risk tensors. D1/D2 comparator calculations, if retained for diagnostics, do not add a track code or a second command ABI; qualifying command tags remain the five ABI tracks A1/A2/A3/C1/C2.

Bind each selection to the ABI fields exactly: `policy_local_index` is the selected K+1 policy slot; `source_global_row` is resolved on-device through `ordinary_row_map` or `continuation_row_map`; `candidate_identity_code` is the stable device numeric identity; `action_id`, `goal_xy`, `goal_heading`, `target_identity`, `route_override`, `fallback`, `route_status`, `route_cost`, and `risk_cost` populate the corresponding `FiveTrackDeviceActionCommandV1` fields. Preserve the sampled action's exact old log probability for that same local slot. `FiveTrackPpoTransitionV3` binds the source table/map digest, route query/result rows, selected command, selected-versus-executed action, per-tick macro outputs, lifecycle masks, reward/outcome, RNG/recurrent state, and validation status as defined by the ABI. This route producer supplies its selected device tensors and command fields to the shared consumers; the action/macro owner owns native command consumption and the PPO owner alone owns the canonical row/batch writer and validator. They must be wired tensor-to-tensor under the ABI, without host extraction. This slice adds no route-specific transition, digest, serializer, report sidecar, or decoded host reader. All these dynamic fields stay on-device through the transition write; the only terminal host boundary is unchanged opaque device-produced bundle bytes for I/O.

Update `build_route_feasible_candidates`, `candidate_feature_tensor`/`score_candidates`, and the Plan C branch of `_prepare_decision` so C1/C2 and any in-scope comparator scores use device tensors for feature encoding, feasibility, ETA/route cost, opponent risk, utility, masking, sampling/argmax, and selection. Apply the shared Plan C view map: ordinary local slots `[0,K)` map through `ordinary_row_map` to source-global rows; local continuation `K` maps through `continuation_row_map[0]` to existing global `continue_index`. Preserve the existing candidate identity/action/track/goal/route and exact selected local-slot log probability. Gather the selected values into `FiveTrackDeviceActionCommandV1` on device, then pass that tensor directly to the approved native simulator consumer; no compact host payload or Python action dispatch is allowed. Keep native legality, target revalidation, remasking, and safety as final authority, with all dynamic predicates/results device-side under the ABI. Apply route cost once under the existing policy-score unit contract. Do not change Plan A U/P semantics or its focal-slot route override. Lowest canonical row wins deterministic ties; C1/C2 stochastic sampling and exact log probability remain bound to the selected local slot. Invalid inputs follow the shared device-gated no-op/typed failure path.
