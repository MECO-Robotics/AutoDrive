# Pass 1 plan: whole-compute GPU-only MECO runtime

**Role:** Pass 1 planner artifact
**Status:** Proposed; implementation requires exact-head independent Pass 3 approval per tranche
**Base:** `origin/main` at `41584a2c90cabeb6da5eb126f432f898c46bbbb1`
**Objective:** Close the user's explicit GPU-only requirement across the complete MECO runtime: observation and snapshot construction, tracking and commitment state, candidate/route features, simulator physics and safety, and training/evaluation numerical work. This is a separate umbrella plan; it does not replace the Plan C or Plan A route-decision plans.

## Runtime contract

Treat the user's instruction as **no CPU numerical computation and no CPU numerical fallback** in training, fitting, inference, simulation, evaluation, or validation. The only permitted host work is compute-free I/O and orchestration: process/device scheduling, lease management, device-memory allocation, kernel dispatch, IPC, filesystem/network reads and writes, and typed control/error reporting. Host code may parse immutable configuration/control metadata to dispatch work; it must not decode/transform numeric world state, generate features/candidates, compare tracks, integrate physics, compute model/loss/metric values, or decide actions.

All dynamic numeric state and computations remain on the explicitly selected WX9100 device. Host transfers of dynamic values are prohibited before the relevant computation and decision complete. The allowed terminal boundary is an opaque device-produced byte buffer written/read by host I/O; host code may not reformat, aggregate, hash, or numerically inspect it. A static administrative value or one selected action may not be called “compute-free” by convention if deriving it requires reading device values. Every host operation and every transfer must be classified in a versioned residency contract, with an allowlist and traceable byte/event evidence. Unsupported operations fail closed. No CPU numerical fallback exists in production paths.

This runtime contract does not authorize stopping or reconfiguring active training. Preserve r4, its checkpoints, and both WX9100 leases. Defer **all device, simulator, and behavior tests** until r4 is terminal and both physical WX9100 leases are independently confirmed released. No test may acquire, probe, compile for, or contend for these devices before that gate.

## Dependency order

1. **Integrate and review route decision prerequisites.** Complete the actual Plan C live evaluator, candidate builder, C1/C2/D1/D2 scoring/selection path and integrate it, then complete the separate Plan A A1/A2/A3 all-node route/support/scorer/selection path against the shared route API. Use their current Pass 1 plans as the narrow contracts. Keep the 64-row API chunk cap with stable global mapping and on-device reassembly. Do not start this whole-runtime integration until each prerequisite is exact-head Pass 3 approved and integrated. No claim that existing scaffolding meets this dependency.
2. **Freeze the residency and state contract.** Publish a versioned manifest contract covering device identity, backend/kernel set, numeric state layouts, host allowlist, forbidden operations/fallbacks, RNG ownership, synchronization/copy instrumentation, checkpoint bytes, source identity, and error behavior. Build a complete source-to-sink map for all five tracks and both training/evaluation entry points. The contract must include Phase 2 collection/fitting and supervisor workers, not only policy inference.
3. **GPU observation and snapshot path.** Move raw numeric observation decoding, normalization, visibility filtering, sensor fusion, track association, recurrent observation state, and snapshot assembly onto the selected device. Preserve the separation between physical truth and policy-visible estimates. Keep raw transport/config I/O on host; host code must not parse observations into numeric Python objects or construct per-entity rows. Device snapshot tensors must include physical/environment state, observations and track identities, commitments, recurrent state, RNG, model/optimizer state, rollout/replay state, and validation cursor. Materialize snapshot bytes on device; host may write opaque bytes only.
4. **GPU tracking and candidate/commitment path.** Represent sensed tracks, candidate specifications, commitment identity, goal/heading, legal masks, and candidate feature tensors with fixed-capacity tensor tables and stable integer identity/order. Perform association, stale-track rejection, commitment continue/replace logic, goal snapping, capture/eligibility predicates, candidate expansion, recall checks, route query mapping and feature extraction on device. Preserve current Plan C K-prefix and continue-slot semantics, Plan A all-node support, immutable global row order, and native final safety authority. No Python loops, strings, per-row dictionaries, scalar extracts or host candidate specs may influence the live decision.
5. **GPU simulator state and physics.** Make the device state authoritative from reset through terminal transition. Port all numerical simulation steps that can change the world or score: robot and mechanism dynamics, collision/footprint, motion/action tick progression, fuel/energy, collection, shooting, scoring, ferrying, occupancy/route maps, visibility/observation sensors, terminal/reward signals, and safety/remasking inputs. Run existing HIP/tensor physics only where exact dispatch audit proves coverage; implement missing kernels or stop. Keep native legality and safety checks as final authority, but execute their numerical predicates on device. No CPU stepper, geometry/raster loop, event check, or recovery fallback is permitted.
6. **GPU training, fitting, and evaluation numerics.** Keep model forward/backward, policy distributions and selected index, hidden-state updates, rewards/returns/GAE, rollout storage, PPO ratios/clipping/entropy/value loss, optimizer update, supervised U/B/P and C fitting, target masking, minibatch order, replay/log-prob checks, calibration/evaluation metrics, paired differences/intervals, aggregation, and readiness statistics on device. Preserve exact sample order, checkpoint/resume determinism, score estimand, mask/target authority and track-specific learning semantics. CPU may schedule jobs and copy opaque completed artifacts; CPU statistics or validation cannot gate a result.
7. **GPU artifacts and checkpoint transport.** Define device-produced tensor/byte snapshots for checkpoints, manifests, replay/event records and scorecards. Host code may allocate paths and perform byte-for-byte file I/O, but may not reconstruct numeric JSON/CSV rows, hash/aggregate dynamic outputs, inspect losses, or derive readiness flags from tensor values. Device-side validators produce typed pass/fail tensors/status bytes; host orchestration may route those status bytes without interpreting numeric content. If a required library makes this impossible, fail closed and propose a separately reviewed change to the compute boundary, not an unapproved CPU conversion.
8. **Full five-track call graph integration.** Route every production training, supervised collection/fitting, live inference, evaluation, checkpoint/resume, and fallback path for A1/A2/A3/C1/C2 through the same residency contract. Deterministic fallback and error handling must also be device-computed; unavailable kernels or device mismatch abort the attempt. Keep r4 and existing checkpoints/source untouched. Build a fresh source-bound manifest only after the pinned Phase 0 chain above and complete Phase 2 train-case closure/artifact validation pass. A one-case warm-start slice, unbound effective config, absent human estimand/margin approval, or launch-ready state is not qualification eligibility.

## Validation gates

- **Before r4 releases both WX9100s:** documentation and code review may proceed. Do not compile/import HIP/CUDA kernels, probe GPUs, run parity/profile tests, run simulator/game-behavior tests, start training/fitting/evaluation, or acquire competing leases. No device or simulator tests are included in this planning pass.
- **After manual stop and verified release:** validate both physical WX9100 identities and exclusive leases before any test. Run small pure tensor-kernel parity fixtures, no-host-compute/sync instrumentation, end-to-end profiler traces, and all-five-track state/observation/candidate/physics/training/evaluation parity in that order. Check that no CPU numeric implementation is reachable, including exceptional/fallback paths. Tests must cover snapshot/resume, RNG determinism, track identity/commitment changes, >64 route chunks and cross-chunk order, collision/safety, scoring/collection/ferry, all target families, and paired evaluation results.
- **Simulator behavior gate:** after device parity passes, run reproducible seeded end-to-end evaluation exercising every changed physics, observation, tracking, candidate/commitment and decision path. Inspect simulator records/replays for legal/executed actions, collisions, scores, pickups, shots, ferry, remasking, fallbacks and terminal outcomes. Follow project `AGENTS.md`: restart dashboard services on the exact checkout, verify service process/source, APIs and all served assets, then generate a fresh replay and inspect provenance. Report scenario, seed, replay ID and results. Unit tests alone are insufficient.
- **Training gate:** only after the exact Phase 0 receipt/freeze/closed partition, preregistered paired controls, separately approved human estimand and margin artifacts, current intake revalidation, full Phase 2 train-case closure, five valid warm starts, production non-diagnostic manifest, exact two-WX9100 post-lease attestation, and independent reviews of each tranche may a new campaign start. Retain checkpoint/update/source bindings, two-device fair evaluation scheduling, no starvation/barrier, and validation-only evaluations. Distinguish `launch_ready`, `qualification_eligible`, qualification, and promotion; none imply the next.
- **Pass 3 gates:** reviewer checks each tranche at exact pushed head and then audits the integrated full call graph, device traces, parity, simulator/replay, dashboard currentness, all five tracks and absence of CPU fallbacks. A kernel, prototype, utilization graph, unit test, or partial A/C residency is not whole-compute GPU-only evidence.

## Nonclaims and stop conditions

This plan does not claim that the device path exists, that any prototype is approved for whole-branch reuse, that current training is GPU-only, or that Phase 0, Phase 2, qualification or promotion is complete. If any numerical compute, dynamic-state parse, host scalar read, CPU fallback, unreviewed semantics change, missing simulator transition, or opaque-artifact limitation is found, stop and amend the plan or fail the tranche closed. Do not relabel numeric work as orchestration or serialization to pass the boundary.
