## Objective and scope

Connect the existing single-candidate `run-validation` CLI to a five-policy coordinator and a truthful dashboard rollup for A1, A2, A3, C1, and C2. Keep each policy's state, reports, checkpoint bindings, and three-round streak independent, while using one immutable calibrated `meco-qualification-v5-gpu-bootstrap` protocol with implementation ID `meco-v4-cluster-episode-device-percentile-v1`. Schedule each evaluation on one exclusively leased WX9100 while a separate, qualification-ready five-track campaign continues fair, non-starved training across all five lanes on the other WX9100.

The live r4 diagnostic campaign cannot be upgraded into this qualification campaign. Its diagnostic split, unbound evaluation, and `qualification_eligible=false` status are historical diagnostic evidence only. Keep it untouched until the user manually stops it; after all its workers are terminal and both leases are independently confirmed released, any qualification run must use a new, source-bound campaign and the frozen v5 protocol.

This tranche does not add or change curriculum gate math. `training_curriculum.evaluate_promotion` and `meco_qualification.consume_validation_round` remain authoritative for whether a report passes or promotes. Current `consume_validation_round` rejects historical v1-v4 protocols for promotion and requires the v5 GPU-bootstrap protocol, exact current `source_identity()`, complete frozen case coverage, matched-reference/D0 evidence, and valid report bindings. The coordinator schedules the existing per-policy `run-validation` operation, preserves its immutable reports and state, and surfaces those results without inventing a second qualification decision. The existing `preflight-stage1` is metadata-only: even `ready` does not prove checkpoint bytes, reproduce current source/factory identity, execute an evaluation, or qualify a track.

This plan depends on the separate whole-compute GPU-residency work being implemented and reviewed first. Every coordinator-launched numerical or algorithmic operation must obey the user's GPU-only requirement: training updates, candidate generation/scoring, route/risk computation, paired evaluation, calibration, and statistical/bootstrap calculations run on GPU. Host work is limited to orchestration, lease management, and artifact I/O. CPU fallback, a missing GPU assertion, or an unbound status is a hard failure.

## Existing behavior and precise gap

- `frc_defense/meco_qualification.py` accepts one `--candidate-policy` and a state file bound to that policy. It persists the `CurriculumState`, a last-round summary, and a neighboring `qualification-status.json`. The status includes protocol, bundle/checkpoint identity, gate result, CIs, qualification flag, and streak summary.
- The current `run-validation` runner validates one target round and invokes the existing promotion gate. `consume_validation_round` accepts only the v5 GPU-bootstrap protocol for promotion, verifies frozen cases/seeds and source binding, and uses `training_curriculum.evaluate_promotion`; reports are digest-bound. A failed round resets the active streak, and a protocol change starts a new streak.
- `frc_defense/meco_supervisor.py` orchestrates the diagnostic campaign and publishes `qualification_eligible=false`; it does not coordinate v5 promotion reports across five learned policies. The diagnostic campaign manifest/status cannot be repurposed into a qualification manifest.
- `frc_defense/dashboard_api.py` projects a prior curriculum run's `evaluation_history` and `consecutive_passes`. It does not load or validate the per-policy `qualification-status.json` outputs from the MECO qualification CLI.

Missing work is orchestration, cross-report provenance/indexing, lease-aware evaluation scheduling, and a five-row dashboard projection. Do not recreate the curriculum's category/episode success checks, v5 GPU-bootstrap confidence calculations, or three-pass rule in the coordinator or dashboard. Consume results from the existing validator and promotion path.

## Required state and binding model

1. **One frozen protocol.** Complete the full Phase 0 evidence chain and human decisions, source/runtime freeze, disjoint partitions, D0 calibration closure, matched-reference calibration, reviewed margins, and immutable target protocol before any qualification round. The only promotable protocol for this Stage 1 gate is `meco-qualification-v5-gpu-bootstrap` with implementation ID `meco-v4-cluster-episode-device-percentile-v1`; v1-v4 and the checked-in provisional protocol are diagnostic/historical only. Record and pin protocol ID, canonical file digest, separate source/runtime/native-extension identities, target scenario, exact case table and seeds, selected paired-reference identity, D0 calibration bundle, reviewed margins, and safety schema. Every track invocation and report must carry that same protocol ID/digest and match the frozen current source identity. The coordinator rejects a missing or changed protocol, wrong target, or policy status bound to another protocol. `preflight-stage1 ready` is only metadata consistency and never waives these runtime and byte-verification gates.
2. **Five independent policy state streams.** Maintain one dedicated, mutable qualification CLI state file and one separate append-only coordinator index per candidate policy (`A1-state.json` plus an A1 ledger, etc.), with the CLI's required `candidate_policy` value matching the manifest key. The CLI state file is atomically updated/overwritten as rounds complete; it is not an immutable report. Store each round report under a unique, immutable, policy-specific path and never overwrite it. The append-only index references every immutable report digest and records observed state transitions. Never share a mutable `CurriculumState`, reuse a report ID, or let one policy's streak contribute to another. Each state stream references its own latest checkpoint bundle and bound report IDs/digests.
3. **Three-round evidence chain.** Preserve all three consecutive passing round report IDs and content hashes per policy, not just a displayed count. At each completed round, append a record containing track, candidate policy, scenario, evaluation/report IDs and hash, protocol ID and hash, checkpoint bundle ID and hash, category episode/success evidence, case/seed coverage digest, v5 GPU-bootstrap confidence interval and numeric gate verdict, device identity/lease ID, completion time, and CLI promotion decision. The coordinator verifies that the underlying report and state file agree before indexing them. It may report `qualified` only when the authoritative state and immutable reports demonstrate three passes for this policy under the pinned protocol. A failure, aborted round, state inconsistency, or protocol mismatch clears the displayed active streak for that track while retaining history.
4. **Freshness and failure semantics.** Missing status is `not_started` or `unknown`, never `passed`. Invalid hash, stale output, malformed state, wrong candidate, wrong source/protocol, incomplete report chain, or unavailable report is `invalid`/`stale` with an explicit reason. Do not retain a previously displayed green state when current evidence cannot be read. Dashboard refresh must never mutate qualification state.

## Dashboard row contract

Each of the five rows must show the evidence for that policy only:

| Field | Required meaning |
|---|---|
| Track / policy | Exact manifest identity, e.g. A1/A1; validated against state and report |
| Qualification state | Derived only from verified per-policy v5 reports plus authoritative persisted state |
| Round progress | Consecutive passing count out of 3, with report IDs/hashes for all rounds |
| Protocol | Frozen protocol ID/digest and source/runtime identity match |
| Candidate checkpoint | Latest per-round checkpoint bundle ID/digest; no cross-policy substitution |
| Category evidence | `single` and `cluster` counts/rates, complete frozen strata and seed coverage |
| V5 comparisons | Category-level useful-throughput and safety confidence/margin result from the immutable report |
| Training | Lane state, latest update, next fair queue turn, and compatible checkpoint resume status |
| Device / lease | Exact WX9100 identity, indexed device, exclusive owner, and current lease status |
| Freshness / blocker | Generated time, stale/invalid state, and exact failure reason when evidence is incomplete |

Exposure progress may appear in a separate diagnostic field, clearly labeled as scheduler exposure only. It cannot contribute to qualification state or round count.
