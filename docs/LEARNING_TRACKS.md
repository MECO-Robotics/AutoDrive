# MECO learning tracks: research protocol

Status: D1 hand-weighted ranking is implemented as a diagnostic curriculum policy. A1-A3 and C1-C2 remain proposed tracks; none is qualified or deployable.

## Current baseline and boundary

The offense curriculum is an opt-in research path using `TensorThreeVsThreeEnv`, ordinary simulated perception, and outcome-based promotion with draft targets and budgets. Its policy contract remains 137 scalar inputs and eight categorical actions. Keep that contract and the production controller unchanged while establishing the research comparison. D1 records an eight-row action trace in the existing action order: collection action rows 0–3 refer to the four nearest valid sensed tracks in that snapshot; rows 4–7 are the named fixed actions `score`, `intercept`, `ferry`, and `hold`. This trace makes score-to-action provenance explicit, but it does not provide executable goal or constraint descriptors, a general candidate API, or planner route costs. It is not a qualified Plan C interface or ready-made C1 input table.

For a D1 trace, valid collection rows use `collect:track:<index>` IDs, where `<index>` is a per-snapshot sensor track buffer slot, not a persistent physical identity. Empty candidate slots use unique `collect:unavailable-slot:<rank>` IDs. Fixed IDs are `score`, `intercept`, `ferry`, and `hold`. The table preserves action rows 0–7 and the curriculum mask exactly. Named feature values use `null` when they do not apply; route costs are `null` for every row because no per-candidate planner cost is available. The top-four track order follows the active backend's candidate selection; ties can order differently between ATen and HIP. The action mask is the existing categorical prefilter and does not cover later intake deployment or physical pickup-capture clearance, so a valid collect action is not a guarantee of full pickup feasibility.

Do not treat names such as `frc_defense/adstar.py` from the MECO proposal as an audited planner API. Before pose-level or route-costed experiments, identify and qualify a planner feasibility interface that can enumerate legal choices, compute comparable route costs, and preserve deterministic safety constraints. The first candidate-ranking slice must use only currently expressible choices, or introduce a candidate-table interface without claiming route-cost semantics.

The initial snapshot adapter is implemented in `learning_inputs.py`: it emits six 13-inch raster channels and seven globals for the learner slot. Raster confidence and signed-age cells come from FUEL and opponent sensor tracks plus current teammate telemetry; signed age is negative seconds since observation. The ally channel uses the simulator's explicit team telemetry (`sim.pose` for own-team slots), with confidence 1 and age 0. All comparison policies must receive this same feed. Confirm the robot localization/telemetry feed provides equivalent ally positions before any hardware qualification; otherwise replace this source through the shared observation path. Globals retain pose in meters, heading sine/cosine, carried FUEL count, signed time to the next known HUB phase boundary, and match time remaining. Empty raster cells do not assert that the area was observed empty. The current opponent source remains the simulator's one tracked opponent estimate per robot.

## Comparison sequence

1. **Freeze protocol and D0.** Pin source revision, simulator and perception settings, action cadence, scenario/opponent versions, training and evaluation seeds, and metric definitions. Keep held-out opponent families and final test seeds out of tuning. Measure D0 (current deterministic controller) variance first; set any minimum useful gain from those measurements.
2. **D1 then D2.** D1 currently ranks the eight existing masked action rows using fixed, versioned weights and up to four nearest valid sensed pickup tracks. It records its score trace and action-row IDs in each episode record and is available through `curriculum_training evaluate --policy d1`. This diagnostic baseline is not a qualified reference or Plan C candidate API: it does not encode executable goals/constraints, guarantee pickup feasibility, provide per-candidate AD* route costs, or generate arbitrary goals. Add only features available through the shared observation path and represent unavailable values explicitly. D2 adds a predictive opponent model to D1. Keep prediction, strategic ranking, planning, and local collision handling separately timed and logged.
3. **Qualify interfaces before models.** Define bounded/stable candidate ordering, validity masks, output identity and timestamps, and deterministic tie-breaking. Add freshness checks: reject stale, malformed, or mismatched model outputs and resume deterministic control. Safety, action legality, commitment hysteresis, and fallback remain deterministic. Route-cost accounting is blocked on the qualified planner feasibility API.
4. **Add neural tracks in stages.** Start A1 (multiscale CNN dense pose scores) and C1 (candidate-feature MLP) only after their observation/output adapters and the relevant feasibility interface are qualified. Then compare C2 (map encoder with candidate attention) and A2 (topology-aware structured spatial model). Defer A3 (hierarchical pose graph model) until measured evidence justifies graph and deployment complexity. Keep the existing neural architecture study separate; these tracks do not replace it.
5. **Compare and report.** Use paired scenarios and seeds, matched observations, physics, opponents, action constraints, and evaluation budgets. Report outcome uncertainty, safety events, candidate recall where applicable, calibration, and total feature extraction, planning, inference, and decision latency. Compare gross predicted reward with route/risk costs subtracted exactly once. Profile robot hardware only after simulator qualification.

## Evidence and acceptance

Every run that tests simulated behavior must include an end-to-end simulator evaluation of that behavior. Retain and inspect its simulation record; report the scenario, seed, source revision, and result. Unit tests alone do not qualify a track. Evaluate held-out opponent families, perception dropouts, stale inference, and forced model disablement; verify deterministic recovery. Promotion thresholds must be prespecified from qualified references and baseline variance, not inferred from training reward.

If a dashboard replay is used, restart the relevant dashboard services after code changes, verify their health endpoints and that both backend and frontend assets come from the current checkout, then generate a fresh replay. Record replay provenance and mark older-source replays outdated. Reports must state which tests and simulator evaluations ran, their scenario/seed and record or replay identifiers, and whether dashboard currency was verified; disclose any missing check.

## Assumptions

- The current offense curriculum is the first research host; production behavior and the 137-scalar/eight-action policy stay unchanged.
- “Candidate ranking” starts within currently supported actions/targets. Arbitrary-pose A1–A3 outputs and route-costed candidate semantics wait for a qualified planner feasibility API.
- Candidate topology, gross-reward outputs, D0→D1→D2 controls, and A1/C1→C2/A2→A3 ordering are initial hypotheses to measure, not fixed conclusions. A larger candidate set needs a separately qualified feasibility and planner-cost interface.
